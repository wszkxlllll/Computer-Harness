## 一、开发 Agent 通用交付模板

每个 PR 必须提供以下内容：
1. 修改前/后 commit，处理的 F/R/DEV 编号，当前支持范围。
2. 新增反例及修复前真实失败结果；不要只运行复制函数的探针。
3. 正常路径、异常路径及事件/状态变化说明；用户可按文件/函数走读。
4. 实际执行的命令、环境、测试数量与结果；未执行部分单独写明。
5. 是否改变 Provider wire、模型 prompt、事件 schema、工具语义或默认配置。
6. 是否连接真实桌面/使用付费 API，是否有敏感资产、如何保留和导出。
7. 修复/实现/效果验证的不同状态、回滚方式、剩余限制。
8. 新增合同的生产者、消费者、存储/迁移、失效/清理与测试 ID；按路线 3.1 区分现有基础和新能力。没有现有字段不等于禁止新增，但不能只更新类型就宣称完成。

文件拆分按[重构施工表](./module-refactoring-work-plan.md)的 RFT 工单交付源→目标、根 exports、依赖和事件/Provider 对照。B04/E08 是各批迁移都需检查的边界，不只在 DEV-7 才验收。

“不变量回归通过”“功能存在”“实机适用”“效果有益”是四种不同结论。无法可靠执行的场景可以精确拒绝，但每项可用能力也必须有支持场景的成功证据，不能用全部拒绝作为全部通过。

## 四、工单迁移提示

旧 W01 对应 DEV-0；W02/W03/W04/W05 的基础修复进入 DEV-1，明确补 R01/R02/F08 与基础数据校验；W06/W07/W08 进入 DEV-2；W09 拆为 DEV-3 的诊断基础和 DEV-7 的实验；W10 的重构按所属模块持续推进，Monitor 升格为 DEV-5 的完整阶段。新增 DEV-4 与 DEV-6 分别承接 Memory/语义状态与隔离/恢复，而不是把它们隐含在旧工单中宣称已覆盖。

不要再使用“W01..W10都完成，所以所有F项自动关闭”的逻辑。逐项核对支持范围和验收证据。

## 五、值得主动不做的内容

不做固定次数强制Plan；不做全量Memory随截图硬过期；不把sourceID存在当事实正确；不把目标窗口相同当业务值相同；不把源码归档当可执行包；不让子Agent共享GUI写权；不在普通PR上运行私人桌面；不为完善面试话术堆没有消费者的字段。

这些不是待补漏洞，而是应在面试中清晰解释的设计取舍。

长期方向仍保留独占隔离ComputerSession的Execution Subagent；禁止多个执行者争用同一桌面不等于取消该方向。面试案例跟随实际产品机制与证据整理，不单独驱动字段和模块扩张。
