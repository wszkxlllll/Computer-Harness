# Verified Relay startup

`scripts/relay-verified-start.mjs` requires exactly `--release-root`, `--manifest`, and `--manifest-pin`, each with an explicit normalized absolute path. It never accepts an entry override or CLI importer. The fixed entry is `apps/relay/dist/index.js`.

The manifest (at most 64 KiB) and pin (64 lowercase hex characters, optionally one LF) must be independently reviewed, frozen files outside the candidate. The pin is the SHA256 of F010 `serializeRelayManifest(parsedManifest)`, not the raw JSON bytes. Pretty JSON and manifest entry ordering therefore do not change its canonical meaning. No pin or manifest is generated by this entry.

The bootstrap and F010 checker must also reside outside the candidate and be frozen by the deployment owner. Location and hash matching do not authenticate their provenance; this tool is not a signature system. Plain ancestors, no-follow file opens, bounded reads, file identity checks, and a final root/external-source identity recheck precede import. Only F010 `bytes_and_layout_match` can dispatch the fixed entry.

These checks are point-in-time observations, not atomic validation-to-load or process attestation. Deployment still requires immutable releases, a service user without write permission, controlled exclusive switching, and trusted bootstrap/checker/manifest/pin sources. Optional native ws dependencies and the module-resolution environment are not authenticated by this profile. Ordinary existing Relay startup is unchanged.

Library `startVerifiedRelay` accepts an injected importer and filesystem for offline fixtures. This round tests synthetic release files and a fake importer only: no real service import, private configuration, network, or listening socket. `entryDispatched` means the import was requested (including a rejected import); import resolution is not service health because Relay's asynchronous main may still be pending. Reports contain fixed categories and safe profile/revision/digest fields, never absolute paths, file bodies, or raw exception text.

The CLI preserves an existing exit status when import was requested, including a nonzero status set by candidate main; it does not reset that status to zero. Verification/import failure still sets a nonzero status. Independent fixture tool paths are derived from the current test module rather than a particular checkout location.
