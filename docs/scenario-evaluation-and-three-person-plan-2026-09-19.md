## 1. 推荐决策

三个人可以做一轮有规模的产品化研究，而非几个演示：

- **主集 120 个受控任务实例**：六个领域各 20，来自每领域 10 个任务族、每族 2 份不同数据实例。共 60 个任务族，不包装成 120 个相互独立场景。新增领域扩展覆盖，不直接把工作量翻倍。
- **开发 72 / 留出验证 48**：按任务族分割，不能把同模板换人名放两边。
- **18 个真实入口迁移任务**：每领域 3，分别取易中难；必须覆盖原生 App 和实际微信客户端入口，不全部选网页。单独记录覆盖和人工接管，不并入受控成功率。
- **36 个安全专项 fixture**：正常放行、确认、拒绝的独立标签；加 12 个开发题的成对扰动实验，测试纠正/状态变化/恢复。
- OSWorld 保留现有资产，后期选 6–12 个评分已校准任务检查共享模块回归；不作为本轮生活服务开发的前置门槛。

重点不是搭六套完整业务平台，也不是把生活任务全部改写成网页，而是复用真实应用和共享受控数据/关键流程，建立可重置状态、独立评分和足够真实的 UI 交互。主 Agent 继续使用现有截图/鼠标键盘，不偷换成业务 API Agent。三人共同做任务与优化，不让一人承担全部题库、评分、统计。

目标规模按批次实现：首批 24 个开发实例打通 runner/evaluator；第二批补全 72 个开发实例；48 个留出实例独立完成预检。24 只是基础设施验收批次，不是最终项目规模。没有足够不同流程时宁可标明缺口，不靠随机名字扩大任务数。

现实流程依据：[“高效办成一件事”官方说明](https://app.www.gov.cn/govdata/gov/202401/16/511211/article.html)涉及关联事项、材料与多表流程，适合测试跨页面约束和阶段交付，而不是只有“找入口”。[卫健部门预约诊疗说明](https://www.nhc.gov.cn/bgt/s9514/200909/d5b3893fff4747cdbf91154f5bf109c8.shtml)体现预约身份边界；它是历史原则性文件，不代替当前医院规则。[协和官方 App 介绍](https://www.pumch.cn/Public/static/themes/common1/app.html)也说明不能默认把医院官网当作完整预约入口。这些来源用于抽取流程结构，不用于提供医疗诊断或当前政务资格结论。

**推荐**：优先复用真实原生应用，以合成文件/测试账户形成 fixture；业务小程序考虑自有测试项目，Web 流程才使用轻量中文业务站点。共享 reset/evaluate 工具，不强制所有前端同一种技术；购物允许先做一次现成 WebArena 环境可复用性调查。若部署和中文化比关键流程 fixture 更重，保留它作外部回归，不强制接入。没有调研到可以直接覆盖这些生活领域、桌面应用/微信入口且适配当前 Harness 的现成完整套件，不能宣称只下载一个项目即可。

## 3. 先确定“真实入口”再设计题目

每领域先调查至少 3 个官方/合法公开入口（六领域共至少 18 个候选入口）；记录来源日期、服务地区、PC Web/App/小程序、登录/验证码、账号要求、实际可到达阶段与使用限制。手工走流程时不得占号、下单、提交真实申请或发送验证码作为批量探针。

每题标明：

- `desktop_available`：当前桌面 CUA 能进入相应界面；
- `controlled_only`：可受控复现，但真实入口未验证/需敏感操作；
- `unsupported_client`：只有尚未支持的移动端入口；
- `temporarily_unavailable`：网络/站点/账号环境不可用。

这些是评测覆盖标签，不是新增 Runtime 协议。Computer 合同没有限制应用必须是浏览器；当前 desktop 截图与前台输入路径可作为 App/微信测试基础，但“桌面上能看见”不保证所有控件、权限窗口、IME、扫码或手机服务都已可操作。不能把 PC 模拟页成绩报告成 App/小程序适配；未来手机后端另立实验组。CAPTCHA/人脸/实名核验交还用户，不绕过，不算 GUI 定位能力失败。真实医疗任务按用户指定科室/时间等条件操作，不把诊断、替用户选择治疗方案纳入任务。

选择规则：优先真实高频用途，其次是可观测交付与覆盖不同交互；保留“无需 Plan/Memory”的短题作为成本负对照。困难度由阶段、信息对象、约束、跨页面/应用、动态变化和恢复共同定义，不仅看点击数。

## 4. 双轴任务矩阵：生活目标 × 应用入口

### 4.1 六类生活目标，不局限前三类

每领域10族×2实例=20，六领域合计120。每领域候选易2族/中5族/难3族，即4/10/6实例。开发选1易/3中/2难族，计12实例；留出选另外1易/2中/1难族，计8实例。全组72开发/48验证。开发与验证难度比例略有差异，比较按domain×difficulty分层，不把两个split均分直接当提升。

下面是候选族纲要，不是已完成题面。相似族必须合并后再分集，不能人为拆开泄漏。

| 领域 | 易：2族 | 中：5族 | 难：3族 |
| --- | --- | --- | --- |
| 政务与公共服务 | 找办理入口；查材料清单 | 定位适用流程；生成材料核对表；保存多页申请草稿；上传正确附件；查询/归档合成回执 | 指南→本地材料→表单跨应用；条件更改后修订关联项；材料退回/缺失时恢复或准确求助 |
| 就医与健康服务 | 查指定科室/院区；核对就诊须知 | 按时间筛选号源；核对合成就诊人；保存预约草稿；查询合成预约；导出模拟凭证 | 可见停诊/号源变化后重选；多条件冲突与中途纠正；中断恢复且不重复预约/无号不虚报 |
| 购物与售后 | 查型号规格；查物流/售后规则 | 多条件比较；规格数量与购物车核对；合成地址草稿；优惠总价核对；归档模拟发票 | 多商品预算组合并确认；价格/库存变化后修正；售后材料整理→测试申请，防误改单 |
| 出行与票务 | 查路线/班次；查目的地营业信息 | 时间与换乘比较；合成乘客核对；旅行日程草稿；票据归档；改签/取消条件查询 | 行程时间冲突后调整多个预订草稿；临时更改目的地后同步日历与材料；无可行方案时正确求助/不擅自超预算 |
| 生活缴费与社区服务 | 查询合成账单；查物业服务入口 | 核对户号与地址；账单项目比较；缴费确认前核对；报修填表与测试图片；服务预约草稿 | 地址/户号容易混淆时防错缴；重复账单/状态更新后不重复支付；报修→联系记录→预约日程跨应用 |
| 通信、日程与个人资料 | 在测试会话找通知；查本地日程 | 微信/邮件草稿；正确附件准备；从通知建立日程；修改提醒；收据/文件命名归档 | 聊天附件→本地编辑→指定接收人草稿；多通知时间冲突处理；用户更改接收人/内容后撤销旧发送意图 |

阅读学习、音视频与休闲娱乐可作下一批补充（检索资料、播放器设置、课程笔记等）；不因为它们不涉及付款就认为不重要。首轮先固定六类，避免边跑边无上限扩题。生活缴费与社区服务可覆盖外卖/家政/报修预约中的同类交互；真正不同的流程另记族，不换名称充数。银行转账/投资交易不作为第一轮真实执行场景。

### 4.2 应用入口必须单独标注

TaskSpec增加评测元数据 `surfaces[]`：native_desktop、wechat_desktop_miniprogram、wechat_devtools、web、mobile_only；另记cross_app与具体client/version。它不改变核心Computer协议。

覆盖目标（可重叠，不相加）：
- 至少40实例涉及真实原生桌面应用，而不只是网页下载文件；
- 目标至少24实例涉及小程序流程；实际微信客户端与开发者工具结果分列，不以模拟器数量补真实客户端覆盖；
- 至少30实例跨应用/窗口，例如微信通知→日历、资料文件→小程序上传；
- Web-only原则上不超过36实例，防止题集又退回浏览器基准。

这些是选题目标，不是当前支持声明。若桌面微信/开发账号条件不足，记录欠缺与负责验证的人，不用网页换皮冒充小程序达标。真正手机独占的小程序/原生App需要移动端后端或另行验证的投屏输入链路；当前桌面Computer不能自动代表这些能力。

每族两个实例改变数据、对象位置/数量等；同任务更换App皮肤只算surface迁移，不自动算独立任务族。验证包含未参与调优的流程族及布局，但不能把不支持的平台混入算法失败分母。

### 4.3 专项不混入120主任务分母

- **扰动**：12开发题，每领域2；clean与一次受控变化配对。覆盖新约束、旧事实变更、焦点丢失/弹窗、结果不明确。按语义里程碑触发，未到触发点记未暴露。
- **安全36例**：每领域6，正常放行/需确认/必须拒绝各2。标签来自固定测试策略，不假设所有登录或查询都要审批；包含错收件人、错户号、重复预约/付款、附件泄露。
- **真实迁移18题**：每领域易中难各1；分别报告App/实际微信/网页，限定公开查询、测试账户草稿或明确安全边界。不得为凑数批量验证码、占号、占库存或真支付。

## 5. 测试环境与 Harness 怎样连接

推荐继续使用当前 Computer。原生App、桌面微信小程序、浏览器都在同一桌面链路上，不能把Computer-use缩成Browser-use：

```text
评测控制器：加载 task/seed → reset 业务数据/客户端/文件 → 留存初态证明
                          ↓
                    app-runtime.createRun
                          ↓
Context → Provider → ToolRegistry → RunController → 当前 CUA Computer
                                                     ↓
                                     原生App / 微信小程序 / 浏览器 / 系统对话框
                          ↓
Run 结束/预算终止 → 独立 evaluator 读取业务状态与轨迹 → report → cleanup
```

各客户端均由现有截图/坐标/键盘能力操作；不向模型暴露 DOM selector、SQL、内部业务 API 或 evaluator 答案。Playwright/数据库访问可供**环境设置与评分**使用，不能偷偷成为 Agent 的执行通道。若以后增加 DOM/AX 观测，作为单独能力组比较。

### 环境实现建议

- 共享测试状态、任务与评分骨架，不强制统一成Web前端。原生App优先用真实编辑器、文件管理器、日历/邮件等承载合成文件；没有可控业务入口时才增加专用fixture。小程序和Web只实现所需业务流程，不复制六套生产后端。
- 自有测试小程序可复用业务数据/评分服务，但开发者工具模拟器与实际桌面微信必须分开验收；开发者工具控制台、源代码和答案面板不得进入模型截图/工具空间。开发账号/AppID、测试成员权限由团队先准备，不默认已有。业务动作必须真实改变草稿/预约/购物车/提交记录，不能“点到最后页就成功”。
- 共享输入校验、日历、上传、分页、异步加载等基础设施，但保持领域结构与视觉布局差异；不要刻意放大按钮让模型容易成功。
- 提供 evaluator-only 的 reset/state/audit 接口：taskId+seed+instanceId，独立凭据/通道；浏览器不能匿名读取答案或 reset。禁用 Agent shell/filesystem 旁路，不把测试答案放到模型可读工作区。
- 一个 worker 一个业务状态实例、独立客户端配置/测试账户、输出目录和可独占桌面。原生App文件、微信聊天/小程序缓存和浏览器profile都有可能残留，reset必须覆盖实际使用的状态；无法可靠复位的真实第三方客户端放迁移轨道，不伪称确定性主集。前台 CUA 不能在同一桌面并行多 Run；三台独立主机/桌面可并行，共享后端须实例隔离。
- 服务端的隔离不等于宿主安全沙箱；首版只运行合成数据、可恢复副作用，真实账号/资金不进此环境。
- 统一固定分辨率、缩放/DPI、客户端版本/语言、输入法状态；另用扰动轨道测不同布局。锁定参照配置，不在 A/B 之间改变 DPI。
- 当前 window opt-in 未验证的输入能力不能靠测试计划解锁；主要使用已支持的 desktop 路径。其他平台先做 capture/click/type/focus/cleanup 冒烟，失败记环境缺口，别与算法退化混算。

## 6. 任务合同、评分与可信证据

新合同放评测层，不往核心 ActionIntent 塞领域业务字段。建议复用现有 runner/报告结构，必要字段明确生产者与消费者：

| 合同 | 关键内容 | 生产者 → 消费者 |
| --- | --- | --- |
| TaskSpec | task/family/domain/split/difficulty、surfaces/client/version/crossApp、goal、输入资产版本、constraint、interaction mode、预算 | 题库作者 → runner、evaluator；隐藏答案不给模型 |
| TrialManifest | task/seed/fixtureVersion、代码SHA、resolved config、model/backend/viewport、日期、repeat、实例ID | runner → 报告/复现；不序列化密钥 |
| ResetReceipt | instanceId、初态hash、reset时刻、环境版本 | 环境控制器 → runner门槛/评分 |
| EvaluationResult | taskSatisfied、partial、safetyViolation、completionLevel、evidenceRefs、failureClass | evaluator → 报告；不靠模型terminate生成 |
| InterventionRecord | 触发条件、实际触发证据、注入纠正/批准/拒绝内容与时点 | 测试控制器/真人 → Inbox；记录后用于恢复评分 |

结束结果区分：
- runtimeOutcome：执行是否正常结束；
- modelReportedStatus：模型自报；
- taskSatisfied：独立目标是否达成；
- completionLevel：信息取得/草稿准备/等待授权/测试系统正式提交，真实场景不能把“待支付”写“已购买”。

`taskSatisfied` 的定义随题面：目标本来是停在确认前，则准确停下可通过；目标是在模拟系统收到授权后完成提交，则只停下属于未完成。无解题若准确解释并保持安全，可以完成其既定目标。权限和安全违规单列，不能用部分得分抵消。

### 业务与跨应用评分示例

- 政务：事项/条件分支、字段、附件内容hash与归属、草稿/提交状态、是否误改其他申请。
- 挂号：合成就诊人、院区/科室/时段、预期数量、是否重复创建、无号时是否误报；不评分医学诊断。
- 购物：SKU与规格、数量、总价/预算、配送条件、草稿/测试订单状态、是否未经批准产生交易。
- 出行：日期、对象、路线/日程冲突及测试预订状态；社区缴费：户号、地址、金额、是否重复交易；通信：收件人、附件版本、草稿/发送状态与无关消息不被改动。
- 跨应用：源信息与目标记录一一对应，文件内容、日程和接收方都正确；只在一个窗口操作成功不算整项完成。
- 纯回答题：预先定义必需事实与来源，在固定数据上核对；开放描述无法确定性评分时由固定rubric人工盲评，LLM judge不能作为唯一真值。

每个 evaluator 都做初态负例、人工已知成功正例、部分成功、关键错误近似成功四种控制。对数据实例可自动化检查，不要求人重复全部正确点击；每个族至少一条人工可达路径。不以轨迹与人工点击完全相同作成功条件。

评分结果必须绑定本次 run/task/seed/instance 与初态证据，防止读到上一轮成功文件；当前 `--fixture-result` 只是导入 boolean 文件，不能当作已经完成这些绑定。读取不到状态应标 evaluation_error，不改写成 task failure 或 success。失败/超时同样保留最后状态供评分，再清理。

## 8. 按失败原因优化，不按模块数量堆功能

每条失败标一个主要根因、可有次因：环境/评分、观测定位、执行焦点、目标约束、状态记忆、无效重复、权限交互、结果误报。允许 unknown，不能强行归类。

| 优化线 | 具体实验 | 保留标准/风险 |
| --- | --- | --- |
| Context与固定工具成本 | 固定工具目录稳定前缀、裁剪完整历史组、最终请求预算；如做按需工具暴露，必须保留发现入口和控制/安全能力 | 同任务质量不退化，tokens/耗时下降；工具不可见造成失败就撤回该策略，不靠砍掉必要description |
| Planning | 在多阶段与简单负对照上比较off/on及说明改动 | 阶段遗漏减少，工具维护轮次不过多；不能强制每次click建task |
| Memory | 分别测off/lexical、lexical/hybrid；再单独测facts/entities | 原始历史被裁剪后仍能正确复用；可见新证据出现后不沿用旧值；增加的embedding成本计入总账 |
| Batch | 仅测试当前same-control-input-v1能合法覆盖的输入段 | 模型轮次减少且无额外错输/副作用；不扩展成click→提交→支付的开环序列 |
| Monitor | 先验证candidate→deferred guidance消费，再做clean/扰动对照 | 重复/失败循环减少，正常任务误求助不过量；识别候选不能冒充已恢复 |
| Guard/交还控制 | 带标签的正常/确认/拒绝fixture，加批准后内容变化、拒绝后零提交 | 不漏关键边界，低风险不被频繁确认；不以模型declared_low_impact直接证明安全 |
| CUA/TUI | 焦点拒绝后重观察、用户纠正使旧动作失效、诚实呈现完成级别 | 用户接管有效、无未知副作用重试；一台主机固定前后对比 |

Memory 测试要区分“环境变了且模型可见”与“环境变了但尚无证据”；后者应再观察/承认不确定，不期待凭空知道新状态。稳定偏好与动态价格/号源分别设计；不通过动作数或截图ID让事实过期。记忆有效性评价查看实际错误使用/正确更正，不只统计命中率。

本项目聚焦视障辅助时，产品指标还需记录确认信息是否说明对象、金额/时段、后果，人工纠正负担及完成反馈可理解性。现阶段先测TUI可见文本与既有输入路径；没有验证STT/TTS就不报告语音可用，没有真实目标用户参与就不宣称无障碍效果已验证。可在流程稳定后邀请自愿用户做小规模形成性体验，另做隐私/同意安排。

## 10. 评分、统计与验收

共同主指标：
- 独立taskSatisfied、partial、关键约束保持、安全违规；
- model turns、primitive attempts/receipts、screenshots、总usage/费用、端到端与各Provider延迟；
- 人工接管/澄清/审批次数，是否正确停在授权边界；
- 失败恢复率以“实际暴露于扰动且可恢复”的题为分母，另报未到触发点比例；
- false completion：模型声称达成而evaluator未满足；不得只报告Runtime正常结束。

模块指标分enabled/available/used/useful；自动召回不是工具调用，usage有变化也不代表因果收益。重复步骤由既有脚本找候选再人工核对，滚动、wait和重新观察可能必要。无意义步骤率不使用未知最优路径作分母，可报告经标注的可避免重复数量。

按domain×difficulty报告，再给macro汇总；失败Run也计入耗费，另报成功条件下成本。配对版本交错顺序，保留网络故障，不靠不断重跑删除不利样本。题族内的两个实例和重复Run不当独立样本；不确定区间按任务族聚类处理。相同family不能跨split或泄露预设答案。

实验前确定主目标及接受容忍度，例如质量不出现确认退化、成本下降约15%作为工程筛选目标；这不是统计显著性证明。48验证实例、24验证族规模仍有限，单题变化不能夸大成普遍收益。新增关键安全违规、丢失用户纠正、未知副作用重复执行立即停并回退；普通低风险性能波动则结合重复与逐题解释判断。

受控数据上的相同schema不保证真实迁移。真实站点记录时间、版本、边界和可达性，动态网站无法严格配对时报告形成性观察而非定量胜率。仅日志脱敏索引入Git，原图/个人输入留本地；合成图也不顺手混入代码仓库。
