## 问题清单与修正原则

### P0：输入落错控件

最新运行在站内搜索阶段反复将关键词输入 Chrome 地址栏。页面搜索框的 DOM `focused=true` 与真实键盘接收位置矛盾；点击回执完成也不证明后续输入位置正确。

源码证据：`packages/computer-cua/src/managed-browser-host.ts` 的观察脚本用 `document.activeElement === element` 标记焦点，没有在该字段上结合 `document.hasFocus()`；点击脚本使用 `element.click()`。页面内部 activeElement、页面是否拥有焦点、系统窗口/地址栏焦点需要分别验证。不能凭程序化 click 成功推定原生键盘焦点已切换。

方向：先用无模型受控页面复现“地址栏获得焦点→点击页面输入框→原生输入”链路；在准确 target/window 下建立可靠聚焦和输入后验证。明确控件身份再输入，不能通过关闭安全检查或盲目重试解决。

### P0：DOM 指纹不一致或真正过期

最近两次分别 10、13 次 `DOM_CLICK_CANDIDATE_STALE`。旧报告把它全部归因于网站动态变化，证据不足。

新静态发现：观察脚本对 input 的缺省 type 归一化为 `text`、并转小写；`domCandidateFingerprint` 使用归一化后的 `candidate.inputType`。点击脚本指纹却直接使用 `getAttribute("type")`，缺省可能为空，非 input 的 type 也可能被计入。缺省 type 或大小写等情况可能导致静态控件指纹不一致。这证明存在实现口径差异，但尚未通过最小探针确认它覆盖真实 Apple 输入框的 13 次失败。

方向：优先统一观察/执行的角色、名称、type 规范化并补生产路径往返测试；测试不能仅用复制的 synthetic 指纹算法证明自身一致。随后才设计一次有界重观察和重定位。UIA 引用当前可能被映射回 DOM，不能将“改用 UIA”自动视为独立兜底。拒绝前未发送输入才能考虑恢复；结果未知禁止重放。

### P1：模型提示与批处理合同冲突

Runtime 的 same-control 批次只识别 `click` 及 `CTRL+A`，实际浏览器暴露 `click_element`，Mac 使用 CMD；最新 Run 因批次形状拒绝了两个调用。另一次运行把 memory_get 与 scroll 混合，产生六条拒绝事件。

方向：从真实能力生成一致的 Provider/Context 合同；支持经过验证的同控件批次，明确禁止读取结果尚未知时依赖它执行动作。不能把任意多动作直接拆分执行而跳过中间观察、审批或控制命令。

### P1：无进展循环与长任务收尾

重复点击、ESC、输入和滚动持续消耗回合；shadow 不产生普通 monitorGuidance 上下文注入，但仍可能参与 grounding 恢复候选选择，不等同完全关闭监控。

方向：两次同类失败转一次有界诊断/换策略；增加非阻断的简短恢复建议，避免再次变成频繁求人工补充。接近模型预算时预留收尾机会，返回已完成/缺失字段和原因；部分完成不能标成成功。100 次可保留为测试上限，不能当作稳定性修复。

### P1：风险误报仍有尾项

URL 放行在 48 回合测试中验证为零审批，最新任务仍有一次“输入被声明为 observe-only”导致审批。批准只是动作授权，不能修正焦点，因此批准后仍错输。

方向：修效果声明和工具合同；只读输入/导航的负面用例与真实发送、购买、删除用例一并回归。不可因目标写了“全程只读”就忽略动作实际效果；保留高影响确认边界。

### P1：API 延迟与诊断

历史确有 90 秒超时；最新两次分别因预算与取消结束，不能一概称超时。GLM 当前单请求 90 秒、max_tokens 4096、thinking enabled、非流式；上下文工具 schema 重，真实 tokens 与估算存在差距。延迟总值不足以分离网络与服务端生成。

方向：先减少无效回合、裁剪任务无关工具；补响应头/正文完成时延、输入估算与实际 usage、错误类别。固定同题再测延迟中位数/尾部、成功率、额度与人工等待。只在数据支持时调整输出预算或换 Provider；不要盲目关闭不支持关闭的 thinking。

### P1：T2/T3 尚缺真实交付

保存 sheet 曾触发同进程键盘歧义，原生 Accessibility 成功不代表 Harness CUA 产品路径通过。跨应用纠正、旧任务失效、唯一新文件保存需专项验收。

### P2：状态展示、配置与交付

最新取消记录来自 `remote-run-api.ts` 的明确 `command.type === "abort"` 分支，不能据此认定断网触发取消，也不能把取消当作执行障碍根因。产品应区分等待模型、等待用户、取消、预算用尽、部分完成和错误。手机断网提示已有成功反馈，但在新版本需复验去重和恢复清除。

文档原计划仍写“尚未实施”，与现实不符；待提交工作树、构建、进程、公网 Web 需分别记录版本。今天未核对公网或远端，不宣称已部署/已推送。Windows 真机验收留在独立清单。

## 实施路线与验收门槛

| 顺序 | 交付 | 验收后再推进 |
| --- | --- | --- |
| 1 输入与定位最小修复 | 静态 input 指纹往返；地址栏/页面焦点复现；真实 UIA/DOM 路由证据 | 受控输入框重复 5 次正确，地址栏文本不被污染；变体含缺省 type、search、动态重绘；真实过期仍安全拒绝 |
| 2 工具与恢复一致性 | 消除 batch 提示矛盾；有限恢复；非阻断建议；预算收尾 | 原因明确的失败不循环；部分成果可交付且不假报完成；取消/审批回归通过 |
| 3 完整 T1 | 起始网址、搜索、参数采集、表格/来源/时间，未知项如实说明 | 原题成功、独立初态复验及至少一个变体；人工核对结果，无人工代点关键步骤 |
| 4 T2 保存 | 专用目录唯一中文文件，数字标点多行，关闭重开 | 文件存在且逐字一致；验证通过 Harness 路径，非外部工具代做 |
| 5 T3 纠正与跨应用 | 手机中途降低预算、旧动作失效、文档另存 | 新要求进入最终文件，旧方案不继续执行，来源保留；人工切窗标明辅助完成 |
| 6 性能与交付收口 | 同题耗时/调用/成本对照；断网及控制回归；版本索引 | T1/T2/T3 均满足原计划复验要求，队友能按说明独立完成一题 |

性能统计从第一步开始，稳定性通过后再集中做缓存、图片压缩、流式反馈及 Provider 对比。每轮只处理 1—2 个主问题；同类错误连续两次转最小复现，避免再次耗费 100 回合跑整题。

用户配合集中在每个修复后的短验收：配对；观察输入位置；按指定时机暂停/拒绝/纠正；最终核对表格或文件。模型额度与桌面测试沿既有授权边界安排，今天仅更新审计文档。
