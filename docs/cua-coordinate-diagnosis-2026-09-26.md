## Pinned CUA 0.22.2 contract

The [pinned tool reference](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/docs/content/docs/reference/cua-driver/mcp-tools.mdx#L372-L399) defines window click coordinates in the window screenshot's pixel space. On Windows, the [pinned click handler](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/platform-windows/src/tools/impl_.rs#L3484-L3556) applies a per-PID resize ratio when available, converts bitmap coordinates to screen coordinates, and routes foreground pixel clicks through `send_click_synthesized_active_mods`. A successful click receipt means input injection completed; the tool marks the effect unverifiable and does not prove the app changed state.

For foreground text, the [pinned Windows keyboard path](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/platform-windows/src/input/keyboard.rs#L475-L532) iterates the supplied Rust string, encodes each character as UTF-16, appends distinct Unicode key-down/key-up records carrying that code unit, and sends the whole vector in one `SendInput` call. The source does not reuse a single mutable character buffer or substitute the last character while building the vector. Its success receipt still does not read back app text. The controlled comparison below demonstrates different outcomes; further lower-level isolation is needed before attributing the digit changes specifically to Windows/IME handling, CUA batching, or Notepad.

## Controlled batch-versus-paced input check

The revised [diagnostic script](../scripts/cua-type-text-smoke.mjs) ran the batch and paced phases independently on two visually confirmed blank, unsaved synthetic Notepad tabs. Both used PID 90404 / HWND 3212964 and a fresh editor focus click. The batch phase sent the whole string `test 0926` in one adapter call; its receipt reported 9 characters completed, but the owner read the resulting frame as `test 6666` (Notepad status: 9 characters). The paced phase sent the same string as nine separate per-character adapter calls, each followed by a 100 ms wait and fresh exact-window observation; all nine type receipts and waits completed, and the owner read the final frame as `test 0926` (status: 9 characters). Each phase left its synthetic text unsaved and did not use cleanup shortcuts or switch tabs.

Evidence is in the ignored local artifacts: batch [manifest](../runs/diagnostics/cua-type-text-smoke/2026-09-25T22-34-32-328Z-batch-25c98d32-2abe-473c-9552-b10c27c066b9/manifest.json) and `03-after-batch.png`; paced [manifest](../runs/diagnostics/cua-type-text-smoke/2026-09-25T22-36-21-627Z-paced-d2801892-9b41-4650-9a00-eba852c5bdc5/manifest.json) and `12-after-paced.png`. The owner/root performed the visual readback; this note does not reproduce or expose the private screenshots. The result makes stale-tab/focus confusion an inadequate explanation for the batch output, but does not identify whether the divergence is in batched CUA/Windows input delivery, IME/input processing, or the target control. The paced success is a narrow observation, not a validated general workaround or proof of root cause; no typing workaround was implemented.

The script's before/focused/after and per-character PNGs, receipts, dimensions and hashes remain private ignored evidence under `runs/diagnostics/cua-type-text-smoke/<run-id>/`. Do not reuse either tab with its synthetic text; any further test must use a separate fresh blank synthetic tab and receive new live-owner authorization.

This adapter captures through `verify_state`; the pinned verification provider calls `get_window_state` with `_observation_only=true`. Windows `GetWindowStateTool` still resizes the screenshot but skips updating its shared resize registry in observation-only mode (see [provider](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/cua-driver-core/src/expectation.rs#L126-L139) and [Windows handler](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/platform-windows/src/tools/impl_.rs#L1158-L1204), [ratio update](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/platform-windows/src/tools/impl_.rs#L1398-L1416)). The harness's bounds-to-viewport projection may therefore be needed when the image is downscaled. Removing that projection without exact bounds and resize-state evidence could make clicks wrong.

Pinned 0.22.2 documents `get_window_state` as returning both the accessibility tree and screenshot; `capture_mode` is deprecated/ignored, and `include_screenshot:false` skips pixels while retaining the tree. There is no documented screenshot-only window API in this pinned contract. `verify_state` already requests `includeScreenshot:true`, but the live popup-state result was stable with no image. `get_desktop_state` would broaden capture to the full display and is not an allowed recovery. Therefore the change is diagnostic only; no capture fallback or retry policy was added.
