同时，应明确：新增能力属于主动扩展的产品目标，不是旧 F01–F17 自动推导出的全部必修漏洞。每个 Bug 按支持范围独立关闭。可以在受控体验可用后暂停扩张、优化体验，再进入后续阶段。

本轮完整阅读两份 V2 文档，并检查当前 Runtime 的一次性 start/finished、CommandInbox/Approval、Trajectory 写入/flush、Memory/Context 及 Stage 6 实验矩阵。源码未变化，因此未重复运行上轮已执行的 179 项测试和 9 项复现探针；没有新 API 或桌面实验。上轮证据见[外部审计复核](external-audit-confirmation-2026-09-17.md)。

## 2. 需修正的两个文档冲突

### V2-02：新评测表不能替代既有单模块对照

DEV-7 提出的 recent-only/+Plan/+Memory/+Plan+Memory/+Monitor 可以作为后续组合实验，但省略了 raw baseline、独立 Batch 组以及 Fact/Entity 两种 Memory 的区分。

保留既有 P/C/B/M1/M2/N 作为单模块效应矩阵；后续再增加组合和 Monitor on/off。新增窗口捕获/UIA/background/Guard 策略必须在对比双方保持一致，或单独列为实验变量。

DEV-7 是最终冻结与总结，不是首次模型效果比较。DEV-3/4/5 各自完成后，用 Development 做小规模对照再决定参数和默认值；Validation 留给阶段确认。这样无效策略能够及时停用，不必开发所有模块后才发现不合适。DEV-8 的工具检索和只读 Subagent 也不互为硬依赖，可以分别验收。

## 3. DEV-2 开始前要写清的三份合同

### V2-03：TUI 会话、Run 与追问

当前 `RunController.start()` 只能调用一次（`packages/runtime/src/run-controller.ts:312`），finished 后拒绝新命令（`:668`）。V2 的“持续 Run”和验收 T09“连续两个 Run”尚未解释任务结束后用户追问的行为。

第一版建议约定：

- TUI 应用会话可持续存在，同一时刻只拥有一个执行中的 Run。
- 运行期间的回答/纠正进入该 Run 的 Inbox；审批等待时需先作废审批并处理纠正，不能直接当批准。
- Run 结束后新请求创建新 Run、新目录、新审批状态；旧 Action/Approval/Computer handle 不继承。
- UI 保留旧记录用于查看；若需要追问前一任务，显式选取摘要/引用作为新 Run 输入，标记为历史信息，执行前重观察。
- Run Memory 暂不静默跨 Run 搬运。若要继承任务和记忆，需要独立 continuation/import 合同与来源、有效性规则。

这使产品能够持续交互，同时保持现有 Run 生命周期清晰。第一版也可完全不提供跨 Run 上下文继承，但需在界面和验收中说明。

### V2-04：人工接管和批准恢复不能复用同一套暂停动作

当前 `pause()` 只允许 running，waiting_approval 会拒绝；普通 user_input 也明确不能绕过 pending approval。V2 的“编辑/审批前 quiesce”方向正确，但必须补可执行状态转换。

建议明确：请求接管 → 关闭新动作调度 → 处理请求级取消/旧响应失效 → 已派发动作 settled 或 unknown → 确认可接管。仅收到按键不能显示“已停止”。

审批展示本身不必创建一个会把自身审批作废的指令 revision；用户开始纠正/改变目标时则作废旧审批。批准请求必须指向原 candidate 和当前有效 epoch，恢复目标后再检验前置条件。当前审批、纠正、Abort、迟到 response 同时到达时，由单一调度点确定先后。

需要写出至少 running、waiting_approval、takeover_requested、quiescent、unknown 的转换及事件，决定哪些为 Runtime 状态、哪些仅是应用控制状态；不要让 TUI 和 Runtime 各自维护一份“是否已停止”。

### V2-05：跨 Run 的执行阻塞归谁维护

DEV-1 X02 要求 cleanup 超时后新 Run 不能盲用未决 session，DEV-6 又要求持久未决标记不被换 Run 清除。当前只有 Run 内 `unresolvedActionId`，这不足以满足要求。

必须有应用/环境层面的执行所有权：以 Host 确定的环境身份标识当前被控制的桌面，保存 owner、连接/session generation、是否仍有在途动作和阻塞原因。不能只用模型生成的 runId 或新 socket 名当环境身份。

DEV-2 至少做到同一应用进程内，旧 Run 未确认停止时不能把同一桌面交给新 Run；明确多进程尚未支持。DEV-6 再补持久记录、启动核对和受控解除流程。不同桌面/VM 不应被全局一刀切阻塞。

清理超时后的“返回给用户”和“允许再次控制桌面”是两个决定。超时调用仍可能晚完成，必须定义迟到完成如何释放资源且不能改写已经终结的 Run 事实。

## 4. DEV-3/4 前需补的权威性与预算细节

### V2-06：CurrentInstructionView 是派生视图，不直接成为用户授权

V2 已明确 Host Policy 和 Approval 不由模型改写，这一点正确。但“当前有效目标/约束由主模型提议”与“不可裁剪权威输入”之间仍要明确边界。

第一版保留原始用户输入顺序作为权威来源；模型归纳的 InstructionView 标记为派生内容。模型提议 add/replace/revoke 必须带来源，但来源 ID 存在本身不能证明撤销关系正确。对敏感授权的放宽必须走明确人类操作；普通语义归纳有歧义时保留原文并澄清。

不要先删原始“不上传”指令，再指望总结工具永远正确。确需压缩原文时，把压缩、用户确认/不确定性和回退机制作为独立设计与实验。

`instructionRevision` 表示用户指令变化；`decisionEpoch` 可因接管、环境变化而失效。两者不应不加区分地每次截图都递增。需列明各字段生产者、消费点和失效触发，并证明旧响应在 GUI 派发前被拒绝。

Provider preparation 建议拆为 AssetReader 加载/预处理和无网络的序列化/估算；如果含读文件，就不要把整体接口标成无 IO 纯函数。实际发出的请求必须复用被估算的 prepared payload，避免估算后再次组装改变内容。requestId 覆盖每次请求尝试；正常模型与 Risk reviewer 的请求应可区分。

DEV-1 的输出预留字段必须明确消费者和模型输入/输出限制，否则先保持估算文本预算，待 DEV-3 有完整合同再增加。不要留下仅报告、不约束的“硬上限”。

### V2-07：Memory 依赖失效必须由可验证事件触发

DEV-4 的来源、依赖、needs_check 和按需复核路线可行。需要补依赖允许的类型、由谁绑定、哪个事件使它失效、如何进入下一轮 Context。

首版只支持 Host/Adapter 真能产生的 target/session generation 等信号。模型不写依赖不能使不可靠定位变为安全；动作安全仍由执行前置条件保证，不能转嫁给 Memory。

`memory_get` 建议默认 current，显式 history 查询才返回 superseded；对旧数据已有状态标记这一事实应保留。返回 needs_check 不是读取失败，要同时展示待核实原因。模型重写同值只表示工作记忆更新，不表示独立事实验证。

schemaVersion/lastAppliedSequence 需与重放幂等、原子物化和迁移一起实现。模型语义事实、Plan milestone、Runtime 执行事实各自保留来源，不引入一个能凭空读懂截图的自动冲突裁判。

## 5. 接受为正式后续目标，但不扩成当前阻塞

- **DEV-5 Monitor**：可以明确做完 shadow、有限 guidance 和一轮对照；是否默认开启由结果决定。shadow 仍要记录其耗时，因为额外计算可能改变动态 GUI 时序，不能从“prompt 未变”推导完整运行逐位相同。
- **DEV-6 隔离与恢复**：支持范围内的低风险续做和未知高影响结果停止，是有价值的目标。append/flush/fsync 的承诺需写清；半行日志只能按明确尾部修复流程处理，不能通用跳过坏行。
- **DEV-7 交付**：至少一个平台干净安装与退出验收合理。源码候选与可安装包继续分别命名，UI 包选择不应迫使 Runtime 依赖具体平台。
- **DEV-8 扩展**：只读 Subagent 是明确下一版本目标；工具目录较小时，渐进工具检索可独立决定是否启用。长期 Memory、语音和独占隔离 ComputerSession 的 Execution Subagent 仍保留长期方向；本路线限制共用桌面的并发写入，不等于删除既定隔离执行者方向。

项目能力的取舍以产品目标和证据为准。面试案例适合随实际改动整理，不单独驱动增加无消费者字段或强制增加模块。
