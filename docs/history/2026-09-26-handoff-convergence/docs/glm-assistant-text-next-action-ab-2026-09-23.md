# GLM `assistantText` 下一步提示对照实验

日期：2026-09-23。结论：**暂不加入生产系统提示词，也不把 `assistantText` 用作下一动作的执行依据。**

## 问题与方法

已有真实轨迹 T07 两次和 T09 共 39 个 GLM 原生工具调用轮次，`assistantText` 39/39 非空。这与早前简化 wire 探针的 6/6 空 `content` 不同，说明需要以完整 Harness 请求判断。当前要验证的是文字能否稳定描述动作成功后的具体下一步。

使用生产 `DefaultContextCompiler`、`ToolRegistry` 和 `GlmAdapter` 构造 GLM-5.3-Flash 请求。A 为现有提示；B 只在 system 末尾增加一句，要求在 `content` 中写当前动作，以及成功后明确可预测的下一动作，否则写 `Next: observe`。两个请求体经断言只差这句话。脚本在构造后给两组都显式加 `tool_choice: auto`，然后用原生 HTTP 发送；这不是生产 Adapter 默认发送的字段。

六个无个人数据的合成界面状态中，三个有明确后续动作，三个必须等待新观察。每个场景 A/B 各两次，共 24 个请求；顺序交替，无桌面操作。只保存合成请求结构、有限长度的 `content`、工具参数、用量与耗时，不保存密钥、reasoning 或截图字节。24/24 HTTP 成功，均为 `finish_reason=tool_calls`，且保存的响应经生产 GLM Adapter 离线解析均通过。逐次结果见本地 `runs/glm-assistant-text-ab-probe-20260923/rows.validated.jsonl`；该运行目录不应作为公开数据上传。

## 结果

| 指标 | A：现有提示 | B：加一句提示 |
| --- | ---: | ---: |
| 有效原生工具调用 | 12/12 | 12/12 |
| 非空 `content` | 9/12 | 12/12 |
| 严格符合 `Current; Next` 格式 | 0/12 | 5/12 |
| 可预测场景出现 `Next:` 标签 | 0/6 | 2/6 |
| 当前工具名及关键参数符合预期 | 11/12 | 11/12 |
| 平均总 token | 1469.5 | 1551.4 |
| 平均请求耗时 | 13.55 秒 | 14.36 秒 |

人工逐例复核 B 的六个可预测场景：一例先点击已经聚焦的输入框，并说明接着输入查询词；相对**实际 click**，这是 1/6 个可直接识别的下一动作，但当前点击偏离了预期首动作 `type`，没有证明减少模型轮次。一例正确 `type` 却未写下一步；两例提及后续按钮但要求先观察或重新定位；其余两例未给出明确下一动作。因此，按“实际当前动作后的具体下一动作”计为 **1/6**；若要求当前动作也符合预期，则为 **0/6**。对三个不确定场景的六次 B 回复，没有发现直接臆造结果项；其中三次的 `Next` 以 observe 开头，另三次省略下一步。这是少量合成样本的人工判断，不是业务任务成功率。

## 接入判断

一句提示提高了合成样本的文字出现率，但格式遵循只有 5/12。具体下一动作的覆盖为 1/6，且这例伴随一个本可省去的当前点击；本实验没有观察到节省主 Provider 请求。平均 token 多约 82，平均耗时多约 0.81 秒；样本太小，不能将耗时差认定为稳定因果效应。真实任务中已有 39/39 非空，因此这次文字出现率提升本身也不是产品收益。

另有现存消费者边界：[RunController 的 recovery 意图](../../../../packages/runtime/src/run-controller.ts)会把整段 `assistantText` 当作本次失败动作的提示。若全局改成“当前 + 下一步”，下一目标可能混入当前动作的恢复检索。未来若再研究，应先定义结构化、可失效的两段语义及独立消费者，并用真实任务证明减少模型轮次；本轮不修改生产 Context、Provider 或 Runtime。
