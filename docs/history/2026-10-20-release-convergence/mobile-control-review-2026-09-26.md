# Mobile control integration review (2026-09-26)

Status: local source and fixture integration gate passed; real-phone and public deployment acceptance remain open. This review covers the Host, remote Run adapter, relay connector/server, and local launcher.

## Findings and recheck

1. **Paired-device isolation: fixed in source and targeted tests.** `ApplicationRemoteRunApi` records `ownerDeviceId` at Run creation and enforces it for list/get, commands and receipts, subscriptions, and assets. `remote-run-api.test.ts` exercises another paired device attempting to read the Run. This closes the previously identified cross-device access route.
2. **Device revocation and relay resync: fixed in source and targeted tests.** The Host ends live direct SSE streams on device revocation and session rotation (`apps/host/src/server.ts`). The connector now sends cursor-ahead resync as an unsequenced control frame; the relay forwards it before its ordinary increasing-sequence filter (`packages/relay-connector/src/index.ts`, `apps/relay/src/server.ts`). The relay and connector also accept `null` from the `ws.send` success callback on Node 24, avoiding a premature socket termination.
3. **Replay deduplication: fixed for a Host process lifetime.** Start-command keys are retained up to a configured capacity; once full, new IDs are rejected rather than evicting prior IDs. Per-Run command receipts use the same fail-closed capacity pattern (`packages/app-runtime/src/remote-run-api.ts`). A Host restart starts a new in-memory deduplication epoch; callers must refresh state after an uncertain network outcome and must not assume durable exactly-once execution across restarts.
4. **Remote asset path: fixed against ordinary path and junction traversal.** `createFileRemoteAssetReader` rejects invalid path segments, rejects symbolic-link components, checks root containment after `realpath`, and reads through an opened handle while comparing metadata (`packages/app-runtime/src/remote-run-api.ts`). The filesystem API still has a residual race against a hostile local writer replacing path components at exactly the right time; the Run output directory should remain private to the Host account.
5. **Desktop ownership: source path is coherent.** Host and direct CLI both construct `ApplicationSession` with the default environment owner. CUA uses the process-shared lease keyed to the physical desktop, not the pipe name (`packages/app-runtime/src/environment-owner.ts`). This is a code-review conclusion; I did not run two competing desktop processes.
6. **Default launcher: source path and readiness check are coherent.** `scripts/mobile.ps1` defaults to the built Web console served by the Host, with Vite behind `-Dev`. It checks the configured CUA daemon and starts it hidden when absent, then stops only a daemon it started. The Host binds to loopback and constructs a real `ApplicationSession` (`apps/host/src/index.ts`). A separate configured Relay is required for a phone outside localhost.

## Targeted physical-desktop lease recovery review

The later recovery addition was reviewed separately. The dedicated CLI route accepts only the current OS physical-desktop identity, exact Run ID, 64-character SHA-256 identity hash, expected on-disk state, operator, inspection note, external-state-inspected flag, and an interactive `RECOVER <runId>` confirmation (`apps/cli/src/index.ts`). `ProcessSharedEnvironmentOwner.recoverLease` checks the readable record, exact identity/Run/state, and dead owner PID. Ordinary `acquire` still preserves a dead owner's lease as pending cleanup; it does not invoke recovery automatically. I did **not** execute the recovery command or alter the live lease.

Independent command under configured Node 24.19.0: `node_modules/vitest/vitest.mjs run packages/app-runtime/src/environment-owner.test.ts` passed **7/7** tests after the operation-marker fix. These use temporary fixture directories and processes, not the live desktop lease.

**Concurrency recheck: resolved for conforming owner processes.** Acquisition and recovery now both acquire an exclusive, per-identity `wx` operation marker. Recovery holds it through the final exact token/Run/state/dead-PID check, quarantine rename, committed-audit write, and rollback if necessary (`packages/app-runtime/src/environment-owner.ts`). A second recovery or a new Run cannot acquire the marker during that interval. An existing or unreadable marker blocks both paths and is never auto-cleared. A deterministic fixture test checks contention and subsequent acquisition.

**Audit and failure recheck: resolved in source.** Recovery writes a `prepared` audit before moving the lease and a separate `committed` audit after the quarantine rename. If the committed write fails, it restores the lease while holding the marker; if restoration fails, it preserves the marker for manual review. A process crash during the transaction similarly leaves the marker, so no Run silently acquires the desktop. Files are written via temporary file, `fsync`, and rename. The recovery operation itself was not run against the live lease.

## Targeted initial-window picker review

The later initial-window feature was reviewed in source only; the implementation team owns the coordinated final build/test run. Host startup now wires `CuaWindowDiscovery` to `ApplicationSession` and refuses startup if discovery is unavailable (`apps/host/src/index.ts`). Discovery opens a short read-only CUA session, asks for on-screen windows, and confirms cleanup without focusing or input (`packages/computer-cua/src/window-discovery.ts`).

`GET /api/windows` requires a paired device and returns bounded app/title labels with opaque 32-character random tokens, never PID/HWND. Tokens are scoped to that device, expire after 10 minutes, and are invalidated by refresh or consumption (`packages/app-runtime/src/remote-run-api.ts`). `POST /api/runs` requires `targetToken`; Host and Relay reject extra raw-window fields. Start reserves its command ID before asynchronous discovery, so an exact duplicate command can return the original result after its token is consumed. Before Run creation, the adapter re-enumerates and matches exact PID, HWND, app name, and title, then requests `foreground` delivery with that exact window target. A changed or missing target fails; there is no desktop fallback. The existing CUA window binding still verifies identity at session start.

The Host revalidates the paired session after asynchronous window discovery, and Relay rechecks the pending GET session before forwarding a late Host response. Tests in the Host and Relay source cover a device revoked during discovery and ensure private labels/tokens are not returned. A newer overlapping `GET /api/windows` may finish before an older one for the same device, causing the newer response token to become stale when the older request finishes. This is a retry/refresh usability edge; it does not grant another device access or bypass exact-window validation.

The Host worker reported a focused Node 24 window suite passing 16/16; the Relay and Web workers reported their own focused suites. Those counts are author reports, not independently run in this review. No live window inventory, phone connection, or GUI action was invoked by the reviewer.

## Targeted CUA capture-refusal diagnostic review

The latest diagnostics-only change in `packages/computer-cua/src/window-contract.ts` was reviewed against `docs/cua-coordinate-diagnosis-2026-09-26.md`. A refused `verify_state` or exact-target `get_window_state` fallback now reports a fixed tool label, the configured validated numeric PID/HWND, and at most a fixed allowlisted classification such as `UIA_PROVIDER_TIMEOUT`. It does not interpolate the raw driver error code or text, which may contain unrelated window identifiers, paths, or credentials. The fixture refusal test explicitly checks those raw values are absent from the error message.

The capture policy is unchanged: only transient image-schema failures receive up to three read-only exact-target `verify_state` attempts with fixed 75/150 ms backoff; after exhaustion, at most one exact-target `get_window_state` fallback is allowed. A refusal fails closed. The diagnostic change adds no desktop capture, no alternate-window target, and no replay of the already completed click. It classifies the observed timeout; it does not repair capture or prove the native cause. A conflicting known error code and free-text timeout phrase would favor the text heuristic, so classification should be read as a bounded diagnostic hint, not a causal proof.

## Independent window-handoff probe script review

`scripts/cua-window-handoff-probe.mjs` was reviewed separately after the frozen source ZIP; it is not covered by that ZIP's 725-test checkpoint. It uses the existing `ApplicationSession` and Runtime with a local scripted provider, whose only input turn is one fixed Ctrl+O. A fresh blank unsaved synthetic Notepad frame requires exact TTY confirmation before that turn is released. A newly surfaced exact candidate then requires manual PID/HWND selection and confirmation tied to the pending handoff request. The next provider turn only finishes; the script checks a distinct post-handoff session/observation and a single action. It neither selects a file nor types a path, opens/saves a file, broadens to desktop capture, or replays the previous action. The separate parent-observe phase has no tool/action turn, though its explicit foreground window selection can activate the selected parent.

Initial review found and the worker fixed: a missing manifest argument that would overwrite `probe.json`; the parent-observe screenshot path; unbounded/uncancellable waits; an uncleared initial timer; and cleanup completion incorrectly checking for idle after closing. The final source propagates SIGINT to the active Run, bounds phase waits to five minutes and cleanup to fifteen seconds, marks unresolved cleanup pending, and requires closed session plus no active Run and no lease before reporting cleanup confirmed. Unknown cleanup after an otherwise successful phase suppresses success output and sets a nonzero exit code. No live lease is explicitly released or recovered by the script.
