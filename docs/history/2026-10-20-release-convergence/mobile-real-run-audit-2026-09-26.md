# 手机真实任务复核：点击与审批循环

## 结论

本次为只读诊断，不重放动作、不发送消息、不修改 Guard 配置。Run `run-1790426649799-cf6b8820-2f1` 有完整终止事件，记录位于本机 `runs/local/` 对应目录；轨迹、Provider exchange 和 13 张截图均存在。目标、联系人、聊天内容和截图不复制到公共文档。

任务时间为 2026-09-26 20:44:09–20:46:55（中国时间），最终由配对设备 Abort，outcome=cancelled，不是发送成功。模型请求/响应各 13 次；实际提交驱动 7 个动作（6 click、1 type），4 completed、3 refused。请求审批 5 次、用户批准 4 次，这 4 次批准后的动作均未执行。

## 问题一：点击后前台失配，不能当作“未点击”

前五次动作围绕同一表情控件坐标，Guard 均放行。第 1、3、5 次驱动回报 `foreground_unavailable`，明确写的是 **after the click**，且实际前台 HWND 与绑定目标不同；不是带有 `no input was sent` 的执行前拒绝。第 2、4 次返回 SendInput completed，但保存的精确窗口截图没有出现预期表情选择面板。

模型坐标约 (417,1220)，截图确实对应表情按钮位置；驱动完成回执坐标 (1779,1419) 与窗口局部坐标之间存在一致平移。现有证据不支持直接归因 DPI/缩放偏移，也不能单凭截图断言鼠标没有发出。可能是点击后弹层/前台窗口变化、弹层不在原窗口截图中等，仍需实时窗口身份/弹层证据确认，不能猜测 HWND 属于哪个应用。

适配层 `packages/computer-cua/src/cua-driver-computer.ts` 当前把这种结构化 Tool 错误也归为 `refused/CUA_TOOL_REFUSED`。这无法表达“动作可能发生，但后置前台校验失败”。只有含明确未输入证据的路径才归为 WINDOW_FOREGROUND_MISMATCH 并进入已有 handoff；当前这一类既没有正确表达未知效果，又继续让模型反复提出同一点击，值得单独修复。不是适配层自动重试，但模型后续轮次事实上重复操作了目标。

建议：区分执行前拒绝与执行后状态不明，后者进入重新观察/窗口核对或人工恢复，禁止盲目自动重放；不得简单改成前台失配就自动激活、重试同一坐标。使用受控无发送任务验证弹层与 exact-window 截图覆盖。

## 问题二：批准成功，但全文截图字节比较阻止发送

用户纠正已记录（seq64），旧调用正确被 supersede（seq65）。随后点击输入区域并执行 type，截图确认文字已写入。因此“消息发不出去”不是本次文字输入未执行。

发送 Enter / 点击发送被 Guard 分类为 external_commitment，需要确认。五次请求中前四次批准均到达 Runtime（seq94、102、110、118），随后在 seq96、104、112、120 因 `screen changed while approval was pending or approval evidence was unavailable` 被拒绝。没有对应发送动作的 action.execution.started，不能归咎网络丢了批准。

`run-controller.ts` 的 fingerprintObservation/sameObservationFingerprint 对整个截图的编码字节做 SHA256，并要求 byteLength 完全一致。审批前后四对截图仅分别变化 1403、1127、1417、2341 个像素（总 1371216，约 0.08%–0.17%），变化包围盒在侧栏/输入光标附近；保存画面中待发送文本与发送控件仍可见。原始图片字节严格相等会被光标闪烁、侧栏动态等无关变化破坏，导致“批准→新截图不同→重提审批”循环。

这不是 Observation ID 每次变化导致的拒绝；代码已经比较真实图片指纹，但比较的范围/语义过于保守。不能仅靠扩大百分比阈值放行：接收方或关键按钮的小变化可能很重要。

此外，即使字节一致，当前 executeApprovedCall 对 type/keypress 仍会因缺独立焦点证据拒绝，并给出 TUI 的按 I 提示。这是另一个真实存在但本次尚未走到的门槛；手机页面不应收到只适用于 TUI 的恢复指引。

## 问题三：Host 配置与预期不一致

`apps/host/src/index.ts:199` 仍固定 riskGuard=layered，手机入口未沿用 TUI 的 Guard 选择。Monitor=shadow，仅记录候选，不自动干预；本次记录了 repeated_proposal，却不能据此声称已向主模型注入恢复指引。Grounding=off，Computer capabilities.accessibility=false；此次不是 UIA/DOM 元素点击测试。

建议给 Host/手机增加显式 Run 配置入口，展示真实生效的 Guard/Monitor/Grounding 状态。Guard off 只能是用户明确选择的实验模式，说明失去语义审批保护，不能由 Agent 暗中关闭；当前不应提供不存在的启动参数。

## 后续优先级与验收

1. P1：处理执行后前台失配的副作用语义，先阻止重复危险尝试，再定位微信弹层；不与旧 DPI 问题混为一谈。
2. P1：审批针对受保护动作的目标/收件人/焦点等相关证据重新绑定，而非整幅图片逐字节相同。保留真正目标变化时的拒绝；补光标闪烁、无关侧栏变化、焦点改变与控件替换对照。
3. P1 体验：手机 Host 显式配置、当前模式展示与端无关的人工恢复文案；确认“已批准但未执行”在手机可见。
4. 验证先用草稿/测试接收端，发送类真实副作用需单独授权；不能拿公共 Relay 的 fake 后端验收代替这一层。

本次公开中继与配对修复不等于这些原生执行/审批问题已解决。既有 736 项测试没有覆盖本次动态真实 UI 场景，应补对应合同/集成/实机测试，而不是只增加总数。
