## 2026-10-10：非视觉 Web 使用开发路线（代码与浏览器验收完成，真机待验收）

### 用户如何使用与验收

不用专用浏览器，也不用安装原生 App。首轮用 iPhone Safari 打开本项目 Preview；微信／夸克等内置浏览器另做兼容性验收，不与 Safari 首轮混在一起。无障碍语义默认可用，不需要先打开项目里的开关。设备当前 iOS 版本由用户在“设置 → 通用 → 关于本机”自行确认，不从聊天中的版本号推断实测设备。

1. **准备与退出**：先看清屏幕熟悉旁白操作，再尝试仅靠声音。可先在“设置 → 辅助功能 → 辅助功能快捷键”选择旁白，确认自己知道如何关闭；在“设置 → 辅助功能 → 旁白”开启。左右轻扫依次浏览，双击激活当前控件，三指滚动；具体手势以 Apple 设备说明及旁白练习为准。
2. **连接**：新版发布确认后，在 Safari 打开 Preview。已有配对仍有效就继续使用；提示未连接时，在电脑 `http://127.0.0.1:4318/connect` 生成二维码，用手机扫描并由用户本人／可信协助者在电脑确认。不能自动替用户配对，也不能宣称盲人可以不经协助完成所有扫码和电脑授权步骤。
3. **设置验收**：用旁白找到“设置”，切换标准／大字、高对比和减少动画，调整朗读速度和任务通知播报，填写补充回答说明并明确保存。返回后重新进入，核对选中状态与文字仍保留。第一轮建议关掉应用自动播报，单独检查系统旁白；第二轮再开启应用播报，检查是否交叠。旁白不会导致应用播报被自动禁用。
4. **任务验收**：先用安全任务，例如“请在记事本新建一个空白文档，写入‘今天测试手机控制。’和‘我可以随时暂停和修改要求。’两行文字。不要修改、关闭或覆盖任何现有文档，不发送消息，不付款。”按实际准备选择自动目标或整桌面；整桌面会观察其他可见内容，应先整理敏感页面。录音后检查文字，再明确开始；运行中不要同时操作电脑键鼠。验证暂停／继续、补充要求、停止和结果重听；这些可分两个短任务完成，不要求一次把全部控制操作混在同一 Run。
5. **请求与失败验收**：若实际出现提问，检查能否听懂问题并补充；若自然出现审批，先听原因和动作，不确定就拒绝，不能为验收强行制造付款／发送。只有图片才能核实的审批和歧义窗口，记录为“需视觉协助”，不能记独立通过。没有触发的状态记“未覆盖”，不当作成功。连接中断时只刷新／重连，不重复启动任务；用户可主动测试关闭网页后重新打开同一任务，但不关闭电脑 Host 或 Relay。
6. **反馈格式**：每项填“独立完成／需要协助／失败／未覆盖”，补充页面、操作顺序、预期、实际听到的内容及任务大致时间。重点记录控件找不到、名称相同、焦点跳走、反复朗读、文字未保存和无法停止；可以用手机录屏保留旁白声音，先检查录音中没有账号、验证码或其他隐私。反馈无需提供配对链接中的 token 或任何密钥。

协调者可完成部署、接口／轨迹分析、隔离浏览器测试和代码整改；目前不能远程操作用户 iPhone 或验证扬声器里实际读出的内容。真实旁白、语音控制和真人独立使用必须由用户／测试者提供设备证据。首轮不关闭眼睛盲试陌生系统手势，不把键盘／无障碍树通过当作物理读屏通过。参考：[Apple 旁白使用说明](https://support.apple.com/guide/iphone/use-voiceover-in-apps-iphe4ee74be8/ios)。

本轮用户授权将现有 Web 控制台接入系统读屏和键盘操作设施，优先 iPhone Safari + VoiceOver，不新增原生 App，不重做视觉风格。目标是无需知道按钮坐标，也能连接、调整设置、表达任务、了解状态、回应审批／提问、纠正／暂停／停止和阅读结果。无障碍语义默认存在，不用先找到一个“无障碍模式”开关才生效；已有大字、高对比、减少动画和应用播报开关仍独立可调。

### 工程顺序与并行分工

1. **共享原则先确定**：继续用现有 Host／Relay／Run 合同；控件名称、角色、状态与说明由实际页面生产，不新增模型判断、不推断用户残障。系统读屏与应用 TTS 分离，不能通过浏览器可靠检测 VoiceOver 来自动切换。
2. **Luna A：连接、导航、设置**。检查路由加载后的入口焦点、主区域、当前导航、配对状态及偏好保存。控件使用原生 button／input／select／fieldset，名称简洁、帮助文字独立关联；长文本编辑不能每个字符反复通知“已保存”。页面初次就绪或用户显式导航才调整焦点，异步刷新不能抢焦点。
3. **Luna B：任务状态与人机控制**。复用真实状态、pendingRequest、进展和结果；区分持续状态展示与动态通知，去掉重复通知源，避免 SSE 重放、计时刷新或快照轮询形成朗读风暴。审批原因和操作说明在决策前可读；纠正、暂停任务、停止任务和停止朗读不能混淆；请求替换或用户操作导致焦点控件消失时有合理返回位置。
4. **Luna C：任务输入、语音、选窗与截图**。完整标注输入、校验错误、录音状态和选项分组；保留点击开始／结束／取消、识别后编辑再明确提交。截图查看器必须真正隔离背景、约束键盘焦点、支持关闭并恢复焦点。候选名称只能用已有真实证据，不以编号伪造可辨识性。
5. **统一验收**：各线先做组件回归，再跑完整 Web 回归、类型与构建；独立审查公共焦点行为、重复 live region、旧审批保护和语音互斥。浏览器自动化只走隔离夹具，不能操作正在使用的电脑或伪造生产配对。之后才部署 Preview，并使用真 iPhone 完成非视觉验收。

### 必须保留的非视觉边界

- 已有明确应用名／标题的候选可以通过文字导航；必须查看截图才能确认的歧义候选，目前**不能承诺盲人独立确认**。不能只因为图片加载完成就替用户确认，不移除安全校验；提供可读限制和返回自动选择／刷新／取消路径。若未来增加非视觉确认证据，必须单独审查真实来源。
- 页面能读出审批原因不代表能无障碍核实所有图片里的操作对象；仅有截图的信息保持限制，不编造画面描述或暗中添加视觉模型调用。
- 手机端不自动开启系统旁白、麦克风或持续监听；应用播报可以关闭，读屏动态通知仍保留。网站登录准备仍涉及电脑上的手动登录，不宣称已解决验证码和账号认证的独立可访问性。
- 本轮不会改变电脑端弹窗恢复、截图超时、输入执行路径；这些故障与无障碍控制面分别验收。

### 本轮代码交付与审查（2026-10-10）

三条 Luna max 实施线已完成，共用原有 Web、Voice 和 Run 合同，没有修改 Runtime／Provider／Computer、安全审批规则或增加模型调用，也没有引入原生客户端。无障碍语义始终可用，不增加“先开启才能读屏”的模式门槛，保留当前视觉布局与样式。

- **连接、导航和设置**：页面进入就绪状态后定位可读标题／主区域；异步能力刷新不抢焦点。设置选项名称与说明通过真实控件关联，单选、开关和下拉使用原生操作。补充回答说明采用“保存补充说明”明确提交，其他偏好沿原有方式保存；避免每输入一个字符就发送保存通知。连接仍需本机授权，账号登录仍需电脑侧手动处理。
- **任务状态与控制**：`RunAnnouncementCursor` 从现有状态、进展、请求和命令回执产生一个稳定的任务通知区域；首个快照不复读历史，后续有意义的变化才通知，进展去重有界且按 Run 隔离。初始内容仍可通过页面浏览。连接中断不等于任务停止，unknown 不改写为成功。暂停／停止／重试及请求替换导致当前控件消失时，仅在实际焦点丢到页面根部后恢复，不打断用户正在其他位置的操作。
- **请求新鲜度**：如果 SSE 已提供新请求而 GET 快照尚未追上，显示新请求；只有请求身份、审批证据或窗口目标与命令快照不一致时，暂不允许提交该请求并保留刷新入口。相同请求及相同证据的更高事件序号不会普遍锁死控件；清除事件及时移除旧请求。此处理避免读出新请求但发出旧请求的决定，不重放动作。
- **输入、录音与截图**：任务、补充／纠正表单有明确名称和帮助关联；错误可定位。录音为点击开始／结束／取消，计时器不主动朗读，按钮消失后进行有限焦点交接，识别文字仍须检查后明确提交。截图查看器保留背景隔离、双向 Tab 约束、Escape 和返回焦点，缩放操作有名称及极限状态。
- **选窗**：初始候选和任务中交接候选均用已有真实应用／标题关联操作；重名时只用列表位置区分“操作哪一行”，不能拿顺序代替窗口身份。两个预览的最终确认按钮分别关联对应候选及 previewToken。截图才能核实的歧义仍保持视觉确认限制。
- **两套语音**：系统旁白通过页面无障碍树和动态区域工作；应用 TTS 继续按原有开关和通知链路工作。不开启自动播报也能浏览状态；开启旁白不禁用应用语音。网页不能可靠检测旁白是否开启／正在朗读，因此不承诺系统语音与应用 TTS 完全自动仲裁，可在设置手动关闭应用自动播报以避免重叠。

### 2026-10-09：从生活任务倒推体验

并不是所有老人都需要代操作，也不是每件小事都值得启动电脑。手机已经能轻松完成的事项，不应人为绕到电脑。产品优先承接电脑仍有优势或现实限制的部分：阅读和整理长通知、比较多处信息、处理需要下载／打印／保存的文件、准备办事材料和交给家人的清单。具体事项规则仍以实际来源为准，这些是体验设计场景，不是已经验证的办理能力。

| 用户要的结果 | 产品应减少的负担 |
| --- | --- |
| “把这份长通知说清楚，我要带什么、什么时候去” | 不先要求理解文件类型、窗口或技术设置；先给结论，允许重听和展开原文 |
| “把出行要用的信息排成大字清单，方便我带走” | 不只汇报点击过程；结束时说明准备好了什么、文件在哪、下一步怎么用 |
| “帮我把表填好，先给我看，不要提交” | 尊重停在确认前的要求；把待确认的内容与后果说清楚，不用模糊的“允许操作”代替解释 |
| “我刚才没听清／我想改一下／先停一停” | 允许重听、纠正和停止；不要求重说整个任务，不混淆停止朗读与停止任务 |

首屏只让用户表达需求；进行中突出“现在怎样、是否需要我处理”；结束时突出能用的结果。主要界面使用普通中文，不出现Host、Run、回执、DOM等工程术语，不反复显示同一状态，不让解释占满屏幕。设置和诊断逐步展开，但付款／对外发送等关键授权、录音状态和任务停止入口不能藏起来。品牌、真实网址和用户文件名保留实际内容，不能为了全中文而篡改结果。

这仍是待用户验证的设计假设，不宣称替代真实老年人、低视力和盲人访谈；三类使用者的视力、听力、运动能力和数字经验各不相同。

本轮不是重新设计产品，也不把上面的例子做成任务专用提示词、快捷模板或应用特例。保留现有蓝色浅色界面、导航和执行架构，只收敛状态、审批、朗读、结果与失败重试的既有交互。判断标准是用户能否看懂和操作，不是页面上是否写了更多“关怀”说明。真实任务内容、文件名、网址和模型结果保持原样；普通中文用于产品自己的按钮和说明。

## 3. 不能靠文案宣称解决的部分

1. **独立非视觉审批**：当前部分审批和窗口候选需要查看截图。图片替代文本不能证明正确窗口、当前焦点和操作后果。应解释限制并提供拒绝／求助路径，不替用户确认图片。可信的非视觉证据需要另外设计与验证。
2. **完全免触控对话**：持续监听、后台唤醒、自动执行语音命令不属于当前录音合同。浏览器权限、前台生命周期、误触发和隐私均需处理。后续可以研究用户明确开启的有限对话模式、说完自动结束及安全停止命令，但不能用常开麦克风冒充本轮完成。
3. **真实用户成效**：代码和 DOM 测试不能证明老人、盲人、低视力或运动障碍用户都能独立完成任务。后续分别招募用户测试，不将群体混成一个“大字模式”画像。

## 4. 验证与完成标准

- 录音：点击语义、开始／取消／结束、失败清理、识别后仍需检查发送，复用现有测试适配器验证，不偷偷上传新的音频样本。
- 状态：运行、等待审批／输入、暂停、停止中、终态、断连和恢复均由真实快照／事件驱动；计时刷新不能造成连续读屏播报。
- 审批：原因在决定按钮之前可见且可读；证据变化仍阻止旧审批，没有新增跳过安全校验的便利入口。
- 朗读：用户主动朗读不依赖自动播报开关；支持停止、失败反馈和不支持环境降级；与既有语音输出、录音和 Run 生命周期协调。
- 布局：现有单测和类型检查；浏览器实际检查窄屏、字体放大与操作区遮挡。不能把 DOM 测试写成 VoiceOver／TalkBack 或真手机音频测试。
- 回归：现有任务控制、审批、配对、窗口候选、个性化与语音测试保持；不改 Runtime、Computer 和 Provider 协议来迁就展示。
