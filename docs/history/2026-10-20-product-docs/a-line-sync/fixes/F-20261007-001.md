## 接收范围与证据边界

接收 [I-20261007-001](../../../../a-line-sync/issues/I-20261007-001.md) 的首轮响应头超时问题。原始记录表明 GLM 请求准备估算 13002 小于有效 wire 上限 24576，Fetch 在等待响应头约 90 秒后本地超时；没有 HTTP 状态、响应体、usage 或 finish_reason。该证据不证明上游已接收请求，也不证明是输入/输出 token 限额导致，因此本修复不提高 token 限额、不缩短原任务/上下文、不更改 thinking、stream、Guard、重试次数或重放语义。

已核实现 Host 显式配置 90000ms 覆盖 Fetch 客户端默认 240000ms；修改 Fetch 默认值本身不会改变 Host 当前有效期限。Runtime 的旧 `PROVIDER_ATTEMPT_DEADLINE_MS` 仅用于判断是否还剩足够重试窗口，没有创建父级 Abort timer；本修复会将其命名和配置语义明确为 retry reserve，并与 Run 实际使用的 GLM 请求期限一致。保留 120000ms retry window：当单次 retry reserve 加退避大于剩余窗口时，不准入自动重试。

## 实施合同

1. GLM 请求期限默认仍为 90000ms；Host 可用 `GLM_REQUEST_TIMEOUT_MS` 显式配置有界正整数，拒绝空白/非法/越界输入，并在启动摘要输出实际生效值。ResolvedRunConfig 直接入口也校验该值，Provider Factory 与 Runtime retry reserve 使用同一 effective config，不各自采用不一致 fallback。
2. Recorder 只记录严格白名单：安全有效请求配置枚举/数字、真实 Fetch 对同一序列化 body 得到的 UTF-8 字节数、有限阶段/耗时/status、有限取消来源 `local_request_timeout | run_cancelled`。普通网络失败记录 outcome，不伪装成取消来源。Request body/URL/任何 header/密钥/正文/图像/raw error 均不落盘；Fake/custom client 不提供 Fetch 证据时保持 unknown，不能推算或标成实际网络请求。
3. Fetch 锁存 first abort source 与首个取消 reason：本地期限与 Run cancel 竞争时仅报告先发生的一方。等待响应头超时无 status；正文阶段超时保留已经取得的 status；调用方取消保持 cancelled，GLM timeout 仍不可自动重试。Callback 和 recorder 写失败不影响请求结果，不诱发重试。
4. 不新增父级 Runtime timer，不延长 120 秒 retry window，不做真实 API/桌面/服务调用，不改公网、CUA 或部署文件。
