## 1. 基线与目标

PR #15 已合并；修复提交为 `4215599`，其 Windows/macOS/Linux CI 全部通过。公网部署了新版手机 Web，本地新版 Host 已验证配对注册。真实手机审批闭环、读屏体验、各桌面平台的真实操作仍需补验。

已实现：手机配对、任务与结果、截图查看、审批、暂停/纠正/取消；标准与大字简洁、对比度和减少动效设置；可组合的 Context、Planning、Run Memory、Guard 等已有模块。

阶段目标是让用户完成常见生活任务，知道系统在做什么，能够纠正、审批和停止，并留下可信的成功/失败证据。先稳定日常入口与关键链路，再扩大高级研究能力。

## 4. 语音链路

### V1：先把语音变成可编辑任务与纠正

- 手机按一下开始、再按一下结束；录音状态、时长、取消和麦克风权限失败有明确反馈。识别内容完整展示，默认可编辑并确认提交。
- 同一入口支持新 Goal、运行中纠正和回答提问，提交走现有 Run/inbox 合同，不绕开暂停与审批。首版不把普通语音“好的”自动当作风险批准。
- STT 厂商通过适配器替换，密钥保留在 Host/服务端；手机上传至哪个服务、音频保留多久明确可见。默认不长期保存原始音频，记录必要耗时/状态；用户主动允许后才存排障样本。
- 现有 `transcribeOnce` 可承接首版；若引入流式输入，再增加有消费者的 start/partial/final/cancel 事件。必须合并最终完整转写，不能只保留最后一句。
- 中文多句、数字/日期/地点、长停顿、背景噪声、60–120 秒录音、断网、拒绝权限和取消均验证；每例保存脱敏期望文本和人工错误标记。先验证一种服务，第二个用合同测试证明可替换，不阻塞首版。

### V2：结果播报、可打断和辅助通知

- 优先播报最终结果、需要用户回答/审批及明确故障；每步播报为后续可选项，避免刷屏式朗读。
- 支持停止、重播、音量/语速及显示同一份文本；新结果到来不会与旧语音重叠。取消任务同时取消其未播放队列；播放失败保留文字和重试入口。
- TTS 适配器可替换，评估浏览器/系统语音作为低成本候选，不能假定各手机音色、后台播放、自动播放权限一致。首轮用户手势后启用；退后台、锁屏和恢复需真机验证。
- 若使用分块合成，以可读句子为边界，保留顺序与取消语义。测试首段可听耗时、完整播报耗时、截断/重复；不先承诺一个未经测量的延迟数字。

完成标准：手机语音 Goal → 可编辑转写 → 真实本地无外发任务 → 文字结果及可中断播报；同一 Run 至少一次语音纠正。两种手机系统分别列出结果，不把 Web mock 当作真机通过。

## 5. 个性化：从显式设置到 Context

### P1：落实现有回答偏好

当前入口：`apps/web/src/preferences.ts`、`PreferencesScreen.tsx`；消费入口应经 Host → app-runtime 组合根 → `packages/context`。

流程：用户保存 → 本地界面立即应用显示偏好 → 创建 Run 时提交助手偏好白名单 → Host 校验 → 冻结带版本的本 Run 偏好 → Context 投影 → GLM/Qwen 使用 → trace 记录实际投影。

先接 responseDetail、stepExplanation、preferredLanguage。字体/对比度只影响界面，不塞进模型；当前用户要求优先于默认偏好，偏好不能覆盖系统权限/审批要求。稳定投影放在稳定说明区域，减少无谓前缀变化。运行中修改默认只影响下一 Run；若用户明确纠正当前 Run，复用 inbox 并留事件。

完成标准：两 Provider 下对同一任务分别产生简洁/详细或指定语言结果；trace 能定位生效偏好；关闭后无残留；多个 Run/配对设备按既定存储范围隔离；重置生效。浏览器本地偏好不会被宣称为跨设备同步。

### P2：可管理的个人需求资料

候选字段以用户主动输入为先：解释速度、常用出发地、结果格式、操作辅助需求。展示/编辑/删除/导出、来源与最后确认时间都要有入口；不根据字号推断年龄或疾病。只召回与本次任务相关的条目，不把完整资料每轮注入。

用户资料独立于 Run Memory：资料可跨 Run，但 GUI 焦点、窗口、登录状态、余票/价格等不能随之成为长期事实。自动发现的候选偏好需用户确认后保存。先完成显式设置闭环，再考虑自动学习、语义召回和跨设备同步。

## 6. Guard 的个性化配置

### G1：可理解、可回退的策略配置

复用已有 ActionPolicy/审批链，界面提供规则解释和有效策略摘要。拟定首版策略为“标准确认”“更多确认”，逐条展示它们对哪些行为生效；不要靠模糊的“更智能/更安全”命名隐藏规则。

允许配置：指定类别始终确认、禁止类别、允许操作的应用/目标范围、数据对外发送限制、审批过期时间等。只有真实存在且能被可信证据执行的选项才出现在首版；金额、收件人、网站等没有可验证来源时不能假装已精确匹配。

用户偏好可收紧默认规则。允许放宽的低风险项必须范围明确、可撤销、在 Run 创建时冻结；付款/删除/对外承诺等不能靠模型填写“无风险”或关键词缺失直接豁免。研究用 off 若开放，应在本机高级设置明确标记并记入 Run，不作为普通用户默认。

层次：可信合同/范围校验 → 可确定的允许/拒绝/确认 → 高危且不明确时才做有预算的语义评估 → 现有审批。模型的 effect/target/summary 是声明，不能自动当作环境证明；Goal 中出现敏感词不能使所有后续无害动作一律审批。

首版仍逐次批准具体调用。长期授权或短时授权复用另立实验，需能绑定操作、目标、范围、时限及撤销；当前审批修复不等于已实现这些能力。

### G2：效果与可解释性验证

建立脱敏正常/危险/模糊案例，覆盖搜索、填草稿、保存新文件、覆盖删除、付款确认、消息外发、账号设置及隐私传输。区分实际动作阶段，例如“查询票价”和“支付票款”。标签由两人复核，不用规则生成的答案自行证明规则正确。

记录漏拦截、误审批、每任务审批次数、额外模型请求/延迟、拒绝理由可理解度。高影响动作误放行或批准被错误复用立即阻塞发布；普通操作频繁误拦进入优先修复，不通过全关 Guard 掩盖。先受控账户/本地模拟验证副作用，再对获得授权的真实任务验证。

## 8. 每类至少三个稳定 Demo

### D1：六类首批任务，共至少 18 个不同任务

复用已有出行题卡并去除失效日期；下面是任务设计范围，实施前写成带输入、目标与评分的完整任务卡。真实应用/网页/小程序按实际可达性选，不限制全部使用浏览器。

| 类别 | Demo 1：基础 | Demo 2：中等 | Demo 3：复杂/跨界面 |
| --- | --- | --- | --- |
| 出行与票务 | 查询指定日期上海出发车次并筛选 | 比较携程住宿的价格与限制 | 车次/住宿与高德路线联合整理，保留日期预算约束 |
| 医疗与健康服务 | 找到医院科室、地址及就诊流程 | 查询指定院区可预约时段和费用 | 比较院区/时段与交通，形成就诊准备清单，停在预约提交前 |
| 政务与公共服务 | 查询一项办理事项材料 | 根据用户条件确认办理入口、时间和地点 | 整理材料/表单草稿并保存，提交由人工决定 |
| 购物与生活服务 | 查询商品规格和价格 | 比较三款商品/服务的总价与退改规则 | 在测试条件下完成购物/预约草稿，明确收货/日期约束并停在付款前 |
| 文件与办公 | 记事本创建并保存中文清单 | WPS编辑已有文档并另存副本 | 跨浏览器/文件管理器/WPS收集整理信息、保存并重新打开核对 |
| 沟通与日常安排 | 在测试会话准备消息草稿 | 读取授权内容并整理日程草稿 | 组合资料、日历/通讯应用完成安排；真实外发只用明确授权的测试收件人 |

每类三个不同任务均应稳定，不能同一简单题换三种措辞充数。至少一个跨页面/窗口任务；每个任务标注主链路 GUI/DOM/Accessibility、使用模块及权限。没有账号或功能不可达时换成同类相近难度任务，并先更新冻结任务卡。

医疗任务限服务信息与流程，验收不评价诊断治疗；票价余票/商品价格随时间变化，用带时间的页面证据核验，不要求固定答案。真实无法预约/无票应正确报告，不改用户约束凑成功。

### D2：稳定性与录像标准

1. 每个任务卡先冻结 Goal、应用/账号前提、允许范围、停止点、重置方式、人工验收标准和版本配置。每类留一个未用于调参的变体作泛化检查。
2. 同一冻结版本下，每个 Demo 至少连续三次完成验收，并覆盖至少两次独立应用启动/页面重置。18题最低54次完整记录；修复相关链路后重计受影响题，不抹去先前失败。
3. 正常的验证码/审批若任务卡预先允许可记为辅助完成；临时指点坐标、改Goal、代做关键步骤属于非自主完成。自主与辅助分别报告，不混算。
4. 正确报告环境阻塞是合格的约束保持表现，但不计入该任务业务完成的三个稳定 Demo；需要重新准备可完成前提或另选合格任务。
5. 从已达门槛的运行中选一次完整录制：手机发起→过程/必要审批→桌面动作→最终回复→人工核对成果。展示版可剪辑，但保留原始完整视频、Run ID及剪辑说明，不能隐藏人工接管。
6. 录制前隐藏真实姓名/电话/订单/聊天及令牌；私密原件保存在受控本地，Git只存脱敏说明与索引。使用测试文件/测试账号，不录制真实凭据。

最终三平台不要求18题每题全部重跑：每平台先通过第7节能力矩阵和至少3个代表性真实任务，再按要公开承诺的类别补对应 Demo；同一个任务在多个平台运行不算新增不同任务。

## 9. 记录指标与后续优化

复用轨迹、Context trace、模块事件和已有脚本派生指标；不要为能从事件计算的数字再加入协议字段。每次至少记录版本/配置、任务与Run ID、平台、业务完成/辅助/失败/阻塞、结果证据、人工介入和故障归因。

| 维度 | 指标及用途 |
| --- | --- |
| 任务表现 | 人工任务完成率、约束遵守、结果引用、恢复率；工具成功不替代结果核对 |
| 体验/效率 | 总耗时、模型请求耗时、首个有用反馈、动作/模型轮数、重复无效操作、Token、估计成本；人工审批等待单列 |
| Context/Memory/Plan | 实际Context大小和裁剪、缓存服务端可见指标、被纳入且后续消费的Memory、过时召回、计划使用与维护开销；调用次数多不等于有用 |
| Grounding/Monitor/Batch | 候选可用/选择/拒绝、视觉回退、Monitor建议后是否恢复、Batch提前中断及总收益 |
| Guard | 应拦未拦、无害操作误审批、审批重复、拒绝/取消后执行、额外请求和延迟 |
| 语音/无障碍 | 转写关键约束错误、修订次数、STT/TTS首段与完整耗时、播报打断、读屏独立完成与触控失败 |

E1：先固定全功能体验基线，再从暴露的问题选择单变量对照，如语音流式、Context策略、Memory召回或Guard策略。保留同版本同任务的对照；演示任务用于调试后不能再当未见验证集。效果不佳时回退对应可插拔策略，不堆积任务特例。

## 10. 实施完成与暂停条件

每张实施卡须附：负责人与依赖、改动位置/合同、生产消费流、测试命令、实际结果、未验证边界、回退开关、PR及证据索引。文档只用通用路径；密钥与本机配置留本地。

- R/C 阶段：批准/拒绝/取消和基本输入实机闭环，配置可见，才标记“可开始常规手机任务测试”。
- V/P/G 阶段：语音、偏好、策略独立开关与组合通过；新增设置有实际消费者，才标记“功能可交付”。
- T/D 阶段：平台矩阵、18个任务卡、54次最低稳定记录及18份录制齐备，才标记“首批生活场景 Demo 完成”；未覆盖平台/场景单列。
- 出现错目标输入、未批准敏感副作用、取消后继续执行、私密数据泄露或未知副作用被重试，暂停对应链路并修复；普通模型规划失败保留证据、分类迭代，不全部归因驱动。

长期 Memory、Advisory/Execution Subagent、Sandbox、自进化与 Jev 后续实验继续保留。当前先交付上述真实使用闭环；模块策略可替换的能力用于后续受控优化，不要求这一轮实现所有研究方向。

## 12. 认领办法与工作量边界

先从第11节选择任务ID认领，不用一次分完全部待办。建议每人同时一个主要交付加一个不抢桌面的辅助任务；大任务可拆子PR，但保留同一ID及总验收标准。

认领记录格式：`任务ID｜负责人｜协作/审阅人｜依赖是否就绪｜文件范围｜预计交付｜PR｜证据｜状态`。状态统一为未认领/调查中/实施中/待验收/完成/阻塞/延期；目前全部待认领，已有能力只作为起点。

共享文件（protocol、app-runtime配置、Run创建API、Context投影、工具注册）由当轮一个负责人统筹，其他分支通过合同接入；不能三个Agent各自改一套。UI、语音、任务预检可以在合同明确后并行，真实桌面测试排时间段。

最低完整产品里程碑建议先选：B01–B09、M01/M02/M04、L01/L02、U01–U05、V01/V02、P01、G01–G03、S01–S03、C01/N02/N05、T01–T03、D01–D03和O01。这是范围候选，不是本周必须同时完成；随后/研究项按体验和数据决定。18题×3次只是首批稳定验收下限，外加预检、故障复测、跨平台和语音/安全矩阵，工作量不能按18次运行估算。
