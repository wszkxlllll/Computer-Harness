# TUI goal 自动选窗切片

状态：本地实现、离线复审通过；尚未做真实桌面和付费 API 的正向选窗验收。

CUA TUI 首次直接提交 goal 时，会在 Run 前用现有只读 `WindowTargetDiscovery` 取得可见窗口；不截图、不聚焦、不派发输入。`window-target-matcher.ts` 只在唯一候选有完整应用身份或足够完整的标题身份时返回匹配。标题与 goal 同名但 goal 另指明其他应用、同应用多窗口、短语含混、窗口清单失败或无匹配，均不自动开始；TUI 保留 goal 并显示可滚动的窗口列表。用户明确选过窗口/整桌面后，不被自动匹配覆盖；managed browser 仍按其自有目标流程运行。自动匹配只选择当次返回的 PID/window ID，实际窗口身份与前台动作仍由既有 CUA adapter 校验，目标失效不退回整桌面。

这是**本地词面身份匹配**，不是 GLM/Qwen 或 Jev 选窗；窗口清单未传给外部模型。为了降低误选，部分自然说法（例如仅说“携程”，但窗口标题是“携程旅行”）仍需手选。通用规则覆盖办公、通讯、浏览器和系统应用，不内置出行网站名单；真实召回率和错选率尚未知。若用户手选一个目标，它按原 TUI 行为持续到再次手选或重启 TUI；后续 Run 不会暗中改绑。

验证：`pnpm run build` 通过；`pnpm test` 的 51 个 Vitest 文件、617 项通过，Node TAP 19 项通过、1 项因本机符号链接限制跳过。自动选窗定向测试 60 项通过；Sol 复审最终放行了已发现的标题误选、中文复合应用名、异步取消和 12 行窗口列表滚动问题。本轮没有为自动选窗再次调用模型 API 或操作真实桌面。此前真实 GLM＋CUA 整桌面 fixture 任务因目标前台未确认而失败，不能借这批离线测试把它改写为通过；证据见[第三切片结果](./pi-computer-assembly-results-2026-09-23.md)。

另一次不经 TUI 的精确窗口受控任务已取得 background 单击正例：真实 GLM→CUA 窗口截图→一次 click→复观察，fixture 自有 `mouse_up` 证实派发，见[第三切片结果](./pi-computer-assembly-results-2026-09-23.md)。它不能替代 TUI 自动匹配验收。下一步仍需用受控窗口和真实生活应用分别测：窗口发现清单完整性、自动选窗覆盖率与误选率、带浏览器标签的同应用多窗口、中文目标、用户手动改选、目标关闭或迁移后的拒绝，以及绑定后 foreground 输入能否成功。模型辅助候选排名仅作为[默认关闭的 Jev 实验](./pi-window-selection-jev-experiment-2026-09-23.md)；它的联网标题外发、延迟和收益必须单独验收。
