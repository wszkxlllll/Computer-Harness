## 执行顺序与记录

1. 先跑 W1–W3 的单应用与跨窗口链路，再跑 T1、T2；每个用例独立 Run，初态、窗口布局和实际目标先记录。优先从非前台但未最小化的候选窗口启动；最小化恢复单列为未验证边界，不混入通过结论。
2. 对每次候选选择记录：系统枚举的应用名、标题、PID/HWND、Jev 决策或弃权、手动选择、激活结果。动作后记录是否出现新窗口、`new_window_detected`/`foreground_mismatch` 的实际原因，以及确认、`C` 忽略或失败。
3. 逐 Run 保存目标结果、`summary.json`、`trajectory.jsonl`、模型请求/动作/截图次数、Token、耗时、重复或无效步骤、Monitor/Planning/Memory/Guard/Batch 的实际参与证据；人工核对最终页面或文件，不能用“工具 completed”代替任务成功。测试截图只保存在本机证据目录，报告不嵌入隐私画面。
4. 每项判为“通过 / 部分通过 / 未通过 / 环境阻塞”。只要出现错窗输入、截图目标错配、未授权覆盖、无法安全接管新窗口，就停止**当前 Run**并保留轨迹；不能跳过该用例。按下节排查、修复和复测。至少两项出行任务、W1–W3 及跨窗口交接全部有可复核结果后，再作整体放行判断。

## 故障后的重复尝试

- 每个失败用例至少保留首次运行和一次**独立复测**；若首次失败是可恢复的环境问题，修复环境后复测原题。若代码或配置修复，记录修复前后版本，并从可复现初态新建 Run，不用旧轨迹冒充复测。
- 对明确无副作用的连接、枚举或截图失败，可先检查 daemon/窗口身份，再做有界重试。对点击、输入、保存等可能已产生副作用的失败，**先重新观察窗口与文件状态**；结果不明时不得自动重放相同动作，必要时改用新的测试文件名并重新开始 Run。
- 如果复测仍失败，继续定位并进行第二轮修复与复测；不能用另一道题的成功替代原用例，也不能把环境阻塞悄悄记为通过。若出现错窗输入、隐私/财产风险或工具权限边界，停止自动输入，先解决安全问题再复测。
- 报告须列出每次尝试的 Run 路径、初态、故障、采取的修复、复测结果与最终结论；“第一次失败、第二次成功”也保留首次失败证据。
