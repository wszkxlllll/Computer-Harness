# Computer Harness 开发文档规范

版本：1.0  
生效日期：2026-09-01  
适用范围：`Computer-Harness/docs/` 下的计划、实施交接、审计、结果和设计文档。

## 1. 文档先分类，再写内容

每份文档创建时必须选择一种角色：

- **入口/交接**：给实施 Agent 的当前可执行范围；一个阶段只允许一个主入口。
- **计划/设计**：说明目标、边界和方案，不能伪装成已实现结果。
- **审计**：检查代码、文档或证据并给出放行/阻塞结论。
- **结果/证据**：记录实际执行事实、原始错误、输出位置和复现命令。
- **历史/弃用说明**：解释为什么旧路线停止，不再提供可执行新命令。

创建文件前先查 [DOCS-INDEX.md](./DOCS-INDEX.md)。如果只是补充当前阶段，不另造并行入口；如果确实产生独立证据，再新建带日期文件并把链接加入索引。

## 2. 文件头必须包含的元信息

正文标题之后、第一节之前写出以下信息（可用普通 Markdown，不要求 YAML）：

```text
日期：YYYY-MM-DD
文档角色：入口 / 计划 / 审计 / 结果 / 历史
状态：当前执行 / 长期设计 / 历史证据 / 已废弃
当前入口：若不是入口，填写它从属的入口链接
基线：代码提交、环境版本或数据版本；没有就写“不适用”
范围：本次覆盖什么，不覆盖什么
```

文档角色决定写法：入口必须有执行边界和结束条件；审计必须区分独立检查与作者报告；结果必须区分实测与推断；长期设计必须标出尚未实现的能力。

## 3. 入口文档的固定结构

实施入口按以下顺序组织，避免 Agent 自行拼接历史文件：

1. 当前结论和放行范围。
2. 已有基础（链接到证据，不重复复制全文）。
3. 本轮目标。
4. 明确非目标和禁止操作。
5. 执行顺序与门槛。
6. 产物、输出目录和结果记录要求。
7. 失败、取消、未知副作用和清理规则。
8. 完成条件与下一入口。

命令必须带参数说明和作用边界，不能写死作者个人机器路径作为项目要求。会启动 VM、操作桌面、重置快照、调用付费 API 或修改外部仓库的步骤，必须显式标注。

## 4. 审计和结果的证据规则

- **实测**：列命令/时间/版本/输出路径；没有日志或资产就不要写“已通过”。
- **代码确认**：给出文件和符号位置，不能替代运行证据。
- **作者报告**：明确写“作者报告”，不要转述成独立验证。
- **推断/建议**：使用“可能、建议、待验证”，并列出验证方法。
- 新实验必须保留原始错误和失败阶段；不能只保存成功摘要。
- 评分、模型结果、环境可用性、Runtime 合同通过是四类不同结论，不能合并成一个“成功”。
- 隐私截图、API key、账号、完整个人桌面资产不得提交 Git；只记录脱敏索引和本地路径。

## 5. 修改与废弃规则

- 历史证据文件默认不重写、不删除。发现结论变化时，在当前入口增加“路线更新”并链接新文档。
- 旧方案停止执行时，把状态标为“已废弃”，写清替代文件、废弃原因和不受影响的部分。
- 不在多个文件复制完整命令。命令只有一个权威入口，其他文件链接到它。
- 不为一次 bad case 创建新的长期字段、状态或接口；新增内容要写出生产者、消费者、生命周期和当前验证方式。
- 代码、测试、文档三者状态要一致：文档不能宣称尚未存在的适配器、评分或模型实验已经完成。

## 6. 交接前检查清单

提交给实施 Agent 前，作者必须检查：

- [ ] 已在 `DOCS-INDEX.md` 登记，或说明为什么是从属证据。
- [ ] 状态和“当前入口”明确，没有与更新路线冲突的旧命令。
- [ ] 每个关键字段/步骤有生产者、消费者和当前验证方法。
- [ ] 实测、代码阅读、作者报告和推断分开。
- [ ] 资源、权限、网络、模型额度和隐私边界写清楚。
- [ ] 结果落盘路径、失败收尾和正常停止命令明确。
- [ ] 相对链接存在，中文按 UTF-8 读回无替换字符，`git diff --check` 通过。

## 7. 审计回复格式

协调 Agent 向用户汇报时统一使用：

1. 结论：可以推进 / 有条件推进 / 暂停。
2. 本次验证：实际检查了什么，哪些来自作者报告。
3. 关键问题：影响、优先级和责任边界。
4. 文档与下一步：唯一入口、实施顺序和完成条件。
5. 操作边界：是否改代码、启动环境、调用模型或操作桌面。

该规范的目标是让历史资料可追溯、当前指令唯一、未来设计不被误读为已实现，同时不通过删除证据来制造“整洁”。
