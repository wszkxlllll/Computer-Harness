## 修改意见

### 一 先统一窗口证据的适用条件

这是确定的整合分歧，也是当前 Mac T2 的主要相关项。

本地 `packages/computer-cua/src/cua-driver-computer.ts:2160–2194` 在动作前清理旧基线，要求清单完整、未截断，再允许派发。PR 同文件 `3232–3257` 只要求当前精确目标仍在列表中，保存清单的 complete/truncated 标志，后续按不同证据进入恢复或人工选择。两者在同一执行入口修改了行为，不能通过选择一边整文件来解决。

本地严格保护解决了“先改文档、随后因已知证据不足失败”的问题，但固定 Mac 接口缺少完整拓扑证明，所以它本身无法完成 T2。PR 尝试减少过度中断，部分恢复证明仍明确限定 `win32_relationship_probe`。把远端逻辑搬到 Mac 不会自动补出缺失的 owner、sheet/menu、完整性及前台证据。

建议先形成一份精简的判定表，并由 Adapter 与 Runtime 共用明确语义：

| 现场证据 | 建议行为 |
| --- | --- |
| 当前目标的身份、前台、几何及与该动作相关的阻挡关系均已被可信接口确认 | 可以对该目标执行一次获准动作；无关应用的清单不完整不必单独成为失败原因 |
| 仅看到同 PID 或清单里存在目标，附属窗口/前台关系未知 | 不能据此派发需要这些证据的动作；进入明确的能力缺失或人工确认状态 |
| 已知动作 completed，随后清单退化 | 保留动作已完成事实；冻结依赖新关系的后续输入，重新观察或进入有界确认，不能重新执行该动作 |
| 动作结果 partial/unknown | 保留不确定事实；只有经过验证的恢复凭据和匹配的新观察才能进入下一决策，旧动作和旧批次后缀不能重放 |
| 已注册 child 消失、恢复 parent 或接续 sibling | 必须取得对应范围内可信的关系与身份变化证明，不能从缺行或不完整列表推断消失 |

这张表是建议设计，不是已实现能力。实施上保留 F0417 的旧基线清理、负证据诊断、畸形/重复行拒绝；按 T0447 已选的现有 CUA 驱动扩展路线提供目标范围证据，再接入 PR 的恢复机制。全局 complete 和目标范围足够不是同一个字段，不应通过随手补 `complete=true` 混用。

### 二 Windows 多行追加存在旧文本丢失风险

PR 删除 `preValueEmpty` 和非空编辑器的多行拒绝，向驱动发送新 chunk，依赖驱动读取旧值后追加。这个方向能支持正常追加，但需要先修读取失败的分支。

本次独立读取固定上游 tag `cua-driver-rs-v0.22.2` 的 Windows 实现，文件 blob 为 `ef1477e1d6b42052f22d3610100f5243f207fd2a`。在 [`CurrentValue` 到 `SetValue` 路径](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.2/libs/cua-driver/rust/crates/platform-windows/src/tools/impl_.rs#L4382)，旧值读取失败会 `unwrap_or_default()` 成空串，再写入 `current + newText`。因此旧文本不可读时存在被覆盖的条件；后续读回新文本成功也不能证明旧文本被保留。远端文档已披露这个边界，本次源码核对确认该分支存在，尚未做 Windows 实机故障注入。

建议列为非空追加功能发布前的阻断项：在驱动同一受控操作中，旧值读取失败应在写入前返回明确 no-input；成功读取后才写入，并验证最终值。不要在 Harness 另读旧文再拼接一次，这会引入重复前缀和读写间竞态。驱动未修且未验证前，不承诺对已有文档无损追加；可暂时限制这项新能力的可用范围，不能用自动清空或截断代替。

最少测试包括：非空正常追加、空值正常写入、旧值读取失败零写入、读回失败保留 unknown、中文多行及末尾换行、选区存在仍按明确的追加语义处理、过期元素拒绝、取消与同动作不重复执行。

2026-10-04 用户补充 `computer-harness-correctness.html` 后再次核对：本地依赖声明仍为 CUA 0.22.2，原修复方取得的固定上游源码 `d114f35fec05ecd37bf529e5587be86852205b64` 仍存在该分支。另确认外层会将 UIA 操作错误经 `.ok()` 和 `unwrap_or(None)` 变为无结果，之后可能继续其他派发路线。因此修复不能仅把 `unwrap_or_default()` 换成 `?`：必须区分“不支持该模式”和“旧值读取失败”，后者终止整个动作，既不 `SetValue`，也不 fallback 输入。写入已尝试后的错误不得冒充 no-input，仍须保留 unknown 且不自动重试。故障注入需分别断言 SetValue 与后备派发计数均为零，并验证原文保持不变。本项属于非空追加发布阻断条件；与 foreground 换行输入问题分别跟踪。本次新增核对仍是源码证据，未复现本机数据丢失，未修改或部署驱动。

### 三 Mac 多行路由值得移植 但必须独立验收

本地仍把所有包含换行的 type 送入 Windows 专用多行函数；非 Windows 会得到 `MULTILINE_PLATFORM_UNSUPPORTED`。PR 在 `cua-driver-computer.ts:2941` 增加 `current.platform === "win32"` 条件，让 Mac/Linux 回到其原生输入路线。这是可复用的修正点，能避免平台错误路由。

修改时需保留本地动作前证据保护，并把平台分流、工具描述、实际驱动语义一起检查。原生调用成功不代表中文、换行、插入位置、保存编码都正确。Mac 验收必须由 Harness 生成 T2 指定的六行正文，保存 UTF-8 新文件、重新打开，再只读逐字节比对；不能由测试代理预填正文或修正文件后计成功。Windows 保留末尾追加语义，Mac/Linux 不应继承不适用的 UIA elementRef 合同。

### 四 本地 API 与结果完整性修复必须完整保留

PR 修改了 Runtime、Context、Provider 测试及公开事件投影，与本地 API/任务收尾修复存在交叉。特别是 `packages/provider-glm/src/index.ts` 本地有新增实现，而远端主要在相关工具投影测试上变化；没有文本冲突也不保证最终组合行为正确。

必须保留并复验：

- text/wire 两级输入预算及真实请求诊断，不丢 `maxWireInputTokens` 的配置和事件传递。
- 完整目标、最近 GUI 结果及必要工具合同的预算保护；不足时显式报告，不能静默截断后继续假装完成。
- 有 finish 控制时，裸文本不能直接变成成功终态；最后一次请求的结构化收尾仍须准确区分完成与未完成。
- 普通比较/筛选的准确 effect 声明，以及实际审批参数展示；PR 的新候选预览不能覆盖这些本地修复。
- Mac 浏览器默认选择、DOM 输入焦点和地址栏绑定、截图与坐标的平台路由。

这里的优先级是防止整合回归，不能因为远端 CI 全绿就删除本地已经定位并修复的故障路径。API 90 秒超时、输入预算、运行请求数、输出上限应分别报告；本轮窗口故障没有证据支持继续统一加大这些数值。

### 五 手机候选预览和异步恢复先做竞态验证

远端新增了候选预览、图片加载后确认、服务端 previewToken、请求刷新等待，以及 Host/Relay 路由。源码已能看到 cookie/CSRF、捕获后重新鉴权、no-store、候选过期校验等保护。不能把这些已经存在的机制再次报告成缺失缺陷。

本轮未发现足以确认其错误的复现，建议作为必须验证的整合范围：截图采集中取消或撤销设备；先预览 A 再刷新/选 B；旧请求晚返回；候选窗口关闭、身份变化；旧 previewToken 再提交；图片加载失败；两个请求同时预览；请求完成时 Run 已结束。验收看实际是否丢弃旧结果、有无越权返回、是否重复创建 Run，以及电脑仍能继续处理下一个任务。

#### 预览预算与错误诊断补充

预览链路补充核对：固定 PR head 的 `remote-run-api.ts` 设置 `WINDOW_PREVIEW_TIMEOUT_MS = 8_000`，`window-discovery.ts` 在同一传入 signal 下先建会话、查候选、调用 `captureWindowWithRetry`，再查候选；共用捕获函数另有 20 秒上限。有效工作预算受外层剩余时间限制，并非里面一定执行满 20 秒。外层 `captureWindowPreview` 的无参数 catch 将底层错误统一改为 `WINDOW_PREVIEW_UNAVAILABLE`，丢失原因。应先记录脱敏的失败阶段、原始错误码、各段耗时、取消来源和尝试次数，再使排队、会话、前后身份核对及截图共用明确截止时间；清理单独有界且保留其失败。用户另报告 CUA 验证成功但没有图片的路径，需要修复方继续核对实际驱动 verify_state 截图错误分支，不能将身份验证成功当作图片成功。公网图片策略与参数正常目前属于用户提供的排查证据，本轮未独立复核部署。尚无本次请求轨迹证明具体失败是超时，不能据此直接放大时限或宣称根因已定位。

### 六 登录状态隔离适合单独引入

PR 的 `ManagedBrowserProfileService` 按 profile identity 分离持久状态，只有匹配身份的旧记录可以迁移，并通过 create-if-absent 避免覆盖新状态。这个改动与 Mac 原生拓扑问题耦合较低，适合单独验证后引入。

验收应覆盖两个 root/label 交错读取、匹配旧记录迁移、外来或缺 hash 记录不继承、已有损坏新记录不回退、并发迁移不覆盖。恢复的是准备状态记录，不应把读取成功当作网站仍登录，更不能迁移私人 cookie 来绕过正常准备流程。

1. **窗口**：普通目标、真实保存 sheet/menu、同 PID 无关窗口、跨进程附属窗口、CG/AX 失败、丢行/重复行、窗口 ID 重用、几何或 Space 变化。正例能继续，证据不足时零越界输入。
