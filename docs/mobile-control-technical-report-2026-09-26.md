# 手机控制 Harness：技术报告与测试结果

状态：手机控制首版本地实现、回归与本轮实机实验已完成；有条件进入服务器 staging 部署。真手机公网扫码尚待部署后验收，旧 CUA 原生应用/弹层问题未全部通过，不能宣称全场景可用。

## 1. 这次做了什么

新增了手机网页、电脑控制服务和服务器中继。手机负责发任务、看结果、补充要求、审批与选窗；真正的模型调用和电脑操作仍由本机既有 Harness 执行。没有另造一套 Agent 主循环，也没有把 Provider 密钥交给网页或中继。

```text
手机网页（React/Vite）
  → HTTPS 命令 / SSE 状态 / 鉴权截图
服务器中继（Node，部署到用户已有 2 核 / 2 GB 服务器）
  ↔ 电脑主动建立的 WebSocket 连接
电脑 Host（Fastify）
  → ApplicationSession → 现有 Runtime → Provider / CUA
```

公网使用须配置真实域名和 HTTPS。此次未获服务器登录或部署操作授权，仅交付部署材料；本地链路测试不能代替真手机、TLS 和蜂窝网络验收。

## 2. 已实现的模块

| 模块 | 位置 | 职责 |
| --- | --- | --- |
| 手机和电脑管理页 | `apps/web` | Goal、完整回复、截图、纠正、暂停/恢复/停止、审批、窗口请求、二维码和配对设备管理。 |
| 本机控制服务 | `apps/host` | 真实 ApplicationSession 装配、配对确认、会话与 CSRF、命令与事件接口、授权资产读取。 |
| 中继服务 | `apps/relay` | 电脑身份连接、手机到对应电脑的路由、同源网页、事件和截图中转；不运行模型。 |
| 出站连接器 | `packages/relay-connector` | 有界消息、断线/重连、配对注册与撤销、状态补读；不离线重放动作。 |
| 应用层适配 | `packages/app-runtime` | 请求绑定控制、设备归属、命令去重、运行投影和跨进程桌面执行锁。 |
| Windows 启动入口 | `scripts/mobile.ps1` | 复用隔离 Node/配置，默认启动构建好的同源页面；复用或启动 CUA，仅清理自己启动的服务。 |

本地开发模式可用 Vite，但不是普通用户的启动前提。远程协议不能指定任意本机文件或 CUA 方法。本机配对管理接口禁止中继转发。

## 3. 用户应该怎样使用

部署配置完成后：电脑启动入口 → 打开“连接手机” → 生成二维码 → 手机扫码 → 电脑确认该手机 → 手机输入任务。配对不等于批准每个敏感操作；任务中的审批仍绑定具体请求。电脑离线时不能在手机继续操作，也不能误显示为执行成功。

未配置公网中继时，本机页面会明确提示二维码不能供另一台手机连接，不能把 localhost 二维码当成交付的跨网入口。

初始目标选择已接入：手机按应用名/窗口标题选择，服务端用 10 分钟、设备绑定、单次使用的不透明 token 重新核验窗口，不让用户输入 PID，也不因目标失效退回整桌面。丢失响应后以同一命令 ID 重试仍返回原 Run，不会因 token 已消费再创建任务。此前只有运行中的窗口交接，没有开始前的选择，该缺口已补齐。本轮不实现语音、长期个性化偏好、完整离线 PWA 或自动安装系统服务。

### 3.1 先在电脑检查和打开

在本工作树根目录的 PowerShell 中执行（每行独立）：

```powershell
.\scripts\mobile.ps1 check
.\scripts\mobile.ps1 start
```

打开 `http://localhost:4317`。默认直接使用已构建的页面；源码更新后需重建时使用 `.\scripts\mobile.ps1 start -Build`。主 Agent 本轮实际执行 `check` 通过：隔离 Node 24.19.0、CUA 0.22.2、Host/Web 构建均存在；这项检查不运行模型或连接桌面。

启动窗口保持打开，Ctrl+C 退出 Host，并清理启动器自己启动的开发服务和 CUA；已存在的 CUA 不会被该启动器停止。部署中继前，这只是本机预览入口；手机打开 localhost 不会连到电脑。不要同时运行另一个控制同一桌面的 CLI/TUI 任务。

## 4. 审查中实际修复的问题

- 手机之间的 Run 读写、截图、事件和命令回执隔离遗漏：增加创建者设备归属检查。
- 撤销设备后现有 SSE 继续发送，以及认证后等待期间发生撤销的竞争条件：关闭已有流并在订阅前再次核验。
- 超前事件游标无法收到重新同步指令：同步控制事件与业务序号分开处理。
- 去重缓存淘汰后旧命令可能启动第二个 Run：达到容量时拒绝新键，不淘汰已有启动键。
- 资产目录的符号链接/Windows junction 越界：增加路径、链接与真实路径检查；不把不可信本地写入者视为已完全防御。
- Node 24 下 `ws.send` 成功回调返回 `null` 被当作错误：修正双方回调判断，真实握手链路随后通过。
- 全仓测试入口漏掉 Web `.test.tsx`：将组件测试纳入回归。
- 手机窄屏内容截断与长回复展开：按实际渲染溢出显示展开控制，保留输入草稿。
- 审批只有通用原因、看不出要做什么：增加与当前请求绑定的动作预览，展示坐标/按键/字符数量及明确标注未经验证的模型说明，不投影原始敏感输入文本。

### 6.2 下拉框故障已定位到哪一层

只读探测保存在 `runs/diagnostics/cua-window-capture-probe/2026-09-25T22-05-13-833Z-9c120a6b-1ff1-41af-941e-2fa94cf59cd2/probe.json`，主 Agent 已独立读取。四次窗口枚举均找到同一 PID/HWND、相同位置和大小；三次 `verify_state` 返回 stable，但没有图像；随后同窗口 `get_window_state` 明确返回 **UIA provider unresponsive，4 秒超时**。

这说明不是手机没有送达命令，也不是已经证实的坐标偏移：点击确实展开了下拉框，失败发生在下一张窗口截图的获取链路。适配器此前把底层原因压成通用“capture was refused”，降低了可诊断性。已补保守的原因分类与回归测试，Sol 独立复审及 53/53 CUA 定向测试通过；只输出固定类别、工具名和已核验数字窗口身份，不输出任意驱动原文。这不等于底层 CUA 捕获已修复。没有新增整桌面兜底或输入重放。授权会话不足三分钟且刚有成功观察与动作，不能把本次故障归因于五分钟 TTL。

执行者获准单次 Escape 关闭已确认的只读下拉框后，同一只读探测成功：同一窗口身份与几何，`verify_state` 返回 1568×1298 PNG，无需后备调用，随后正常关闭探测会话。证据为同目录 `2026-09-25T22-08-37-119Z-9b9a9463-8825-478b-852c-424946d8e6ed/probe.json`，主 Agent 已核对。它支持“弹层相关的捕获故障”，但不能证明所有弹层都会失败，也不证明根因已修复；这次 Escape 是明确记录的人工恢复，不是模型自行恢复。

恢复后的 12306 Run 终态和上述计量已由主 Agent 从轨迹独立核对。测试执行器途中丢失了内存中的 HTTP 配对凭据，随后只读本地轨迹观察完成，没有绕过设备归属或重新提交任务。这是测试工具会话丢失，不是 Host 自动丢失已执行的 Run；不能据此声称真实手机重连已经验收。
