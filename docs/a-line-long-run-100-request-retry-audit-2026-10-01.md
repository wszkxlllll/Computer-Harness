## 失败链路

1. 地址栏导航阶段正常完成，说明新的地址栏 URL 放行规则没有导致阻断。
2. 进入 Apple Mac 页面后，模型打开了站内搜索浮层。
3. 页面 DOM 多次显示站内搜索框获得焦点，但截图与实际键盘焦点不一致；多次输入都进入 Chrome 地址栏。
4. 地址栏中重复出现 `MacBook Air`，模型连续使用 ESC、点击和重新输入进行恢复。
5. 站内搜索框的 DOM 引用多次失效，产生 13 次 `DOM_CLICK_CANDIDATE_STALE`。
6. 有 2 次模型同时提交不符合批处理合同的多个 Computer 调用，调用被拒绝。
7. 最后一次模型请求尚未返回时，运行收到配对设备中止信号，直接以 `cancelled` 结束。

## API 判断

本次不能归类为 API 超时：

- 最慢请求约 69.5 秒，低于当前单请求 90 秒截止时间；
- Provider 记录没有网络错误或响应错误；
- 结束事件明确来自配对设备中止，而不是 `GLM_REQUEST_TIMEOUT`；
- 100 次模型请求上限尚未耗尽。

API 延迟仍然偏高，平均约 19 秒，并且 45 次请求累计等待约 14 分钟。它显著放大了焦点错误的时间成本，但不是本次终止信号的来源。

## 建议的修复顺序

1. **P0：地址栏与网页输入焦点确认**
   - 在 `type` 前检查浏览器 chrome 地址栏是否处于编辑态；
   - 若地址栏有未提交文本，先安全取消并重新观察；
   - 对“DOM 显示页面输入框 focused、系统焦点仍在地址栏”的矛盾状态直接拒绝输入，要求重新定位。

2. **P0：DOM 过期后的自动重定位**
   - `DOM_CLICK_CANDIDATE_STALE` 后自动获取一次新观察；
   - 优先用最新 DOM 候选，再尝试 UIA 候选；
   - 恢复失败时返回明确的“需要重新观察”，不要让模型盲目重复点击。

3. **P1：减少恢复回合**
   - 为地址栏误输入提供受控恢复动作；
   - 连续两次焦点恢复失败后切换到直接可验证的导航路径，而不是继续输入。

4. **P1：批处理合同修正**
   - 对同一回合的多个 Computer 调用在模型输出侧或运行时提前拆分；
   - 避免把不符合 `same-control` 形状的调用交给执行层再拒绝。

5. **P2：API 性能优化**
   - 缩短重复恢复回合的上下文和图片数量；
   - 限制焦点恢复阶段的推理输出；
   - 保留 100 次上限作为长任务容错，但不把提高上限当作主修复。

## 验收标准

- 站内搜索关键词至少一次进入网页输入框，不能进入地址栏；
- 连续两次 DOM 候选变化不再产生 13 次级别的失败堆积；
- 运行不因一次配对设备中止而留下未说明的“任务失败”；
- API 请求未达到 90 秒超时，且任务能在完成或明确标记“未找到”后正常结束。
