# F-20261012-078: bounded recovery after a closed bound window

The opt-in macOS native-window flow can recover once when a completed close leaves the Run without its bound primary window. Host configuration must supply exactly two distinct, pre-authorized window targets: the primary and a recovery blank whose identity is pinned when the Run opens. Recovery uses the existing `list_windows` and `switch_window` tools, with at most two control-only model requests across the Run. It does not replay the completed close or send the closed window's older screenshots or grounding to the recovery decision. A switch must pass the existing handoff checks and be followed by a fresh capture before ordinary GUI tools resume. Missing candidates, an unselected candidate, a failed switch, cancellation, and budget exhaustion keep their existing waiting or terminal behavior.

The advisory inventory path now preserves the exact completed root binding only when recovery is opted in, the platform is Darwin, the delivery mode is foreground, window switching is enabled, and the completed root action and manual handoff authorization still match. It still returns `WINDOW_TARGET_NOT_FOUND`; formal missing-bound detection then performs a separate fresh inventory and establishes the recovery boundary. In all other cases, the previous invalidation behavior remains in force. Recovery remains within the two exact Host-authorized scopes and does not add an automatic path for arbitrary newly opened windows.

Validation has separate offline and live evidence. The focused Production adapter/RunController regression exercised the completed close, advisory inventory error, formal missing-bound detection, recovery candidate discovery, and rejection of stale input against the closed root. Negative cases confirmed invalidation when recovery is disabled or the action baseline is not completed. The focused test selection passed 3/3 and the Computer CUA package build exited successfully.
