## Windows旧文本丢失条件

固定原生platform-windows/src/tools/impl_.rs约4365–4505：非Foreground delivery且携带元素引用的UIA路径，CurrentValue错误被unwrap_or_default转为空串，再SetValue(current + newText)，存在覆盖旧内容的条件；不限于多行。随后闭包.ok()与Join结果unwrap_or(None)把不同阶段错误折叠，可能进入WM_CHAR备用输入。Foreground提前走另一条SendInput路径，不应说所有Windows输入均触发；没有本机数据丢失实测。

修复必须在原生操作内保留阶段，而非Harness文本缓存：

- 明确模式不支持且尚未写入：才可按既有合同选择备用路线。
- 旧值读取失败：零SetValue、零WM_CHAR，明确no-input。
- 写入已尝试、验证失败或Join阶段不明：unknown，不自动备用或重放。
- 合法读到空字符串不同于读取失败，前者可按授权写入一次。

仅把读取处改成问号错误传播不够，外层仍可能吞错并fallback。测试需对SetValue/备用输入分别计数，覆盖空值、非空、Read/GetPattern/SetValue/Join失败、验证失败、取消和过期元素。这是追加功能发布前阻断项，与旧换行变5和Mac拓扑故障分开跟踪。主协调另核当前Adapter仍保留preValueEmpty门禁，PR22才删除它；不能把原生风险等同于当前已开放非空追加，也不能把门禁当作原生缺陷已修。
